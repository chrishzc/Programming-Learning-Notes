## 1. 設定bypass對象
- **Role（角色）：**
    
    - **例子：** 像是你目前選的 `Repository admin`（專案管理員）或 `Maintainer`（維護者）。
        
    - **實體畫面：** 「認職位不認人」。只要誰當上經理（Admin），誰就自動獲得這個特權，不用一個一個名字去綁定。
        
- **Team（團隊）：**
    
    - **例子：** 專案裡的 `@senior-developers`（資深核心小組）或 `@devops-team`。
        
    - **實體畫面：** 給這幾位資深老手一串特權鑰匙。當半夜系統爆炸（Production Bug）需要緊急修復時，他們不需要等待龜速的 PR 流程，可以直接推代碼救火。
        
- **App / Agent（自動化機器人）：**
    
    - **例子：** 像是 `github-actions` 機器人，或者專門幫忙自動升級套件版本的 `dependabot`。
        
    - **實體畫面：** 給公司的「自動化掃地機器人」一張免死金牌，讓它在半夜自動更新套件、修正安全漏洞時，不需要驚動你人工去按 Approve。
## 2. 設定特權模式（Bypass mode）

當你把某個人或角色加進清單後，右邊可以選擇他們的**特權寬容度**（點擊 `...` 或下拉選單可以調整）：

- **1. Always allow（總是允許，你目前設定的這顆 🌟）：**
    
    - **實體畫面：** 「終身免檢徽章」。
        
    - **效果：** 這個人完全不受任何 Branch rules 的限制。他可以直接 Push、直接 Merge、不寫 PR 也沒關係。因為你是專案唯一的最高審查官，給自己設成這樣最方便。
        
- **2. For pull requests only（僅限 Pull Request 時免受限制）：**
    
    - **實體畫面：** 「快速通關券」。
        
    - **效果：** 這個人**平常還是得乖乖開 PR**（不能直接暴力 Push 到 `main`），但是當他在審查 PR 時，他可以跳過「必須有 1 個人按核准」或是「自動化測試必須通過」的硬性規定，自己直接點下合併。這很適合給不想破壞常規流程、但關鍵時刻需要強行放行的資深成員。

# 4.Branch rules
## 第一類：基礎進出管制（最嚴格的封鎖）

### 1. Restrict creations（限制建立）

- **實體畫面：** 公司規定只有總務可以買新保險箱放進主儲藏室，其他人不准自己搬一個紙箱進來說「這是我們的新倉庫」。
    
- **日常例子：** 菜鳥工程師不能隨意在線上建立一個也叫做 `main` 或 `release-v1` 的分身分支。只有你可以建立。
    

### 2. Restrict updates（限制更新）

- **實體畫面：** 保險箱的投遞口被貼上「全面封帳」的封條。
    
- **日常例子：** 專案要準備對外發表了，今天「封測」，除了在白名單上的你可以緊急修 Bug 之外，其他人都不能對這個分支推送（Push）任何新扣（Code）。
    

### 3. Restrict deletions（限制刪除）

- **實體畫面：** 保險箱用水泥和鋼筋死死地焊在牆壁上，誰都搬不走。
    
- **日常例子：** 小明原本只想刪除自己的個人測試分支，結果手滑選錯，差點把整個公司的 `main` 分支（主程式）給刪掉。有了這條，保全會直接把小明的手推開，不准他刪。

## 📈 第二類：檔案品質與規格檢查（確保東西是好的）

### 4. Require linear history（需要線性歷史）

- **實體畫面：** 辦公室的簽到簿，大家必須像排隊量身高一樣，清清楚楚一前一後排好，不准出現兩個人同時把名字疊寫在同一行（交錯的 Merge Commit）。
    
- **日常例子：** 同事小華在合併程式碼時，歷史紀錄變得很複雜（像蜘蛛網）。這條規則會強迫他必須用 `Squash`（把一堆零碎的紀錄揉成一球）或 `Rebase`，讓主分支的歷史紀錄永遠是一條乾淨的直線。
    

### 5. Require deployments to succeed（需要部署成功）

- **實體畫面：** 新產品在放進總部保險箱之前，必須先送到「隔壁的測試工廠」組裝成功、而且運轉沒有冒煙。
    
- **日常例子：** 你的網頁程式在合併到 `main` 之前，必須先在 AWS 或 Vercel 的測試環境成功跑起來。如果部署失敗（畫面打不開），這條規則就不會讓程式碼合進 `main`。
    

### 6. Require signed commits（需要簽名提交）

- **實體畫面：** 進出儲藏室交貨，不能只在簽到簿上寫「我是小華」，必須拿出刻有個人防偽條碼的「私章」蓋上去才算數。
    
- **日常例子：** 駭客可能會偽造別人的電子郵件來推代碼。勾選這個後，每位工程師的電腦都必須設定 GPG 金鑰簽章。保全只要發現這行程式碼沒有數位簽章，就會判定這是「來路不明的冒牌貨」並拒絕接收。

## 👥 第三類：進階審查機制（PR 的細部隱藏設定）

當我們開啟了 **Require a pull request before merging（合併前需要 Pull Request）**，下面有幾條延伸的法條：

### 7. Dismiss stale pull request approvals when new commits are pushed（有新進度時撤銷舊核准）

- **實體畫面：** 小華拿了一張修改單請你簽名同意。你簽完後，小華走回座位，又偷偷在單子後面多塗改了兩行字。這時候，你在單子上的簽名會「自動消失」，他必須重新拿來給你審查。
    
- **日常例子：** 你幫同事按了 Approve（同意合併），但他隨後又補推了 2 個 Commit。系統會自動撤銷你的同意，強迫你重新看過他新改的內容。
    

### 8. Require review from specific teams（需要特定團隊審查）

- **實體畫面：** 如果這次修改動到了「電路圖」，除了你簽名之外，還必須強迫叫「電子工程組」的組長也過來簽名。
    
- **日常例子：** 專案裡有些改動屬於資安或 UI 範疇，可以指定特定團隊（例如 `@security-team`）必須有人來看過才行。
    

### 9. Require review from Code Owners（需要程式碼擁有者審查）

- **實體畫面：** 公司的核心保險箱裡有分層，動到「財務報表夾」就必須驚動「財務經理」本人；動到「核心引擎」就要驚動「總工程師」。
    
- **日常例子：** 你可以在專案裡寫一個 `CODEOWNERS` 檔案。只要有人改了資料庫相關的程式（例如 `/db/` 資料夾），系統就會強制標記資料庫專家來審查。
    

### 10. Require approval of the most recent reviewable push（需要針對最新推送進行核准）

- **實體畫面：** 只要單子有被動過，最後經手改那筆資料的人，絕對不能是最後蓋章放行的人，必須有第三方雪亮的眼睛。
    
- **日常例子：** 確保最後一次改動程式碼的人，和按 Approve 的人是完全不同的兩個人，避免黑箱作業。
    

### 11. Require conversation resolution before merging（合併前需要解決所有對話）

- **實體畫面：** 大家在申請單上貼了很多黃色便利貼（例如：「這裡的程式碼好像會造成記憶體洩漏？」、「語法是不是寫錯了？」）。在還沒把問題討論完、把便利貼撕掉（Resolve）之前，保全不放行。
    
- **日常例子：** 強迫大家不能已讀不回 Code Review 的意見，必須把所有對話框都點選「Resolve conversation」後，Merge 按鈕才會變綠色。
    
### 12. Allowed merge methods
merge methods情境介紹:

假設專案目前的狀態如下：
- **main** **分支**：目前有兩個提交，標記為 **D → E**。
- **feature** **分支**：開發者從 **D** 點拉出分支，並新增了三個提交：**A → B → C**。
---

1. 建立合併提交 (Merge Commit)

這是 GitHub 的預設行為（`git merge --no-ff`）。

- **合併後的歷史圖表**：
    - `main` 分支會產生一個全新的合併提交 **M**。
    - 提交順序呈現非線性（類似地鐵圖）：`main` 軸線上是 **D → E → M**，而 **M** 同時指向 **E** 與 **C**。
- **特點範例**：
    - **保留所有細節**：你在 `feature` 分支上的 A、B、C 三次紀錄都會完整保留在歷史中。
    - **包含合併資訊**：歷史中會出現一條訊息寫著 "Merge pull request #1 from feature-branch"。

2. 壓扁並合併 (Squash and Merge)

此方式會將 `feature` 分支上的所有變更合併為一個單一的提交。

- **合併後的歷史圖表**：
    - GitHub 會計算 A、B、C 所有的代碼變更，並在 **E** 之上建立一個全新的提交 **S**。
    - 提交順序呈現完全線性：**D → E → S**。
- **特點範例**：
    - **歷史極致整潔**：原始的提交 A、B、C 會從 `main` 的歷史中**消失**，只留下一個整合後的 S。
    - **適合 WIP 多的分支**：如果開發過程中有許多「修正錯字」或「測試」等細碎 commit，使用 Squash 可以隱藏這些雜訊。

3. 變基並合併 (Rebase and Merge)

此方式會將 `feature` 的提交逐一「複製」並重新排列在 `main` 的頂端。

- **合併後的歷史圖表**：
    - 原本的 A、B、C 會被按順序重新放置在 **E** 之後，變成 **A' → B' → C'**。
    - 提交順序呈現完全線性：**D → E → A' → B' → C'**。
- **特點範例**：
    - **線性但保留細節**：與 Squash 不同，它保留了每一次開發的獨立 commit 節點，但不會產生額外的合併提交 M。
    - **SHA 會改變**：由於 A'、B'、C' 的父節點變成了 E（原本是 D），它們會獲得**全新的 Commit SHA**，且會失去原始的 Verified（驗證）簽章。

## 🤖 第四類：自動化安全檢測（工具把關）

### 12. Require status checks to pass（需要狀態檢查通過）

- **實體畫面：** 傳送帶上裝了 X 光自動檢查機。凡是走過來的貨物，都要自動掃描有沒有夾帶違禁品、形狀合不合標準。
    
- **日常例子：** 結合 GitHub Actions（CI 系統）。當同事提 PR 時，電腦會自動幫他跑單元測試（Unit Test）和語法檢查（Lint）。如果自動測試失敗（紅燈），就算你按了同意也沒用，必須等測試修到變綠燈。
    

### 13. Block force pushes（阻止強制推送）

- **實體畫面：** 嚴禁動用「時光倒流」或「記憶消除棒」。
    
- **日常例子：** 阻止任何人使用 `git push -f` 這種暴力指令。這會強行把線上的歷史紀錄抹除並覆蓋，是多人協作的大忌。
    

### 14. Require code scanning results（需要程式碼掃描結果）

- **實體畫面：** 引進外聘的專業資安防爆小組，拿著儀器掃描看裡面有沒有藏炸彈。
    
- **日常例子：** 結合 GitHub 的 CodeQL 等漏洞掃描工具。如果有人不小心把金鑰（API Key）或密碼寫死在程式碼裡，掃描器會發現並拉響警報，直接攔截這次合併。
    

### 15. Require code quality results / Restrict code coverage（程式碼品質與覆蓋率）

- **實體畫面：** 專門的品管（QA）稽核員。除了程式要能跑，還要檢查代碼寫得夠不夠漂亮（Quality）、寫的測試有沒有覆蓋到 80% 以上的範圍（Coverage）。
    
- **日常例子：** 超過設定的複雜度，或者測試寫太少，系統就會報警拒絕合併。
    

### 16. Automatically request Copilot code review（自動請求 Copilot 審查）

- **實體畫面：** 聘請一位 AI 助理保全。只要有人交卷，AI 率先跳出來幫忙挑錯、給建議，幫你減輕第一輪的審查負擔。
    
- **日常例子：** GitHub Copilot 會在 PR 建立時自動留下審查意見。
