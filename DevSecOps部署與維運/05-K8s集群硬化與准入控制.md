# 05 · K8s 集群硬化與准入控制

> **學習目標**：掌握在 Kubernetes 集群中，透過 RBAC 最小化與 Kyverno 准入策略，阻斷不安全部署配置進入生產。

---

## 一、為什麼需要集群硬化？

CI 階段已經掃描過鏡像、通過了 SAST 和 SCA——**但這還不夠**。

```
CI 階段能阻擋的：
  ✅ 鏡像中已知 CVE 漏洞
  ✅ 代碼中的靜態漏洞
  ✅ 未簽章的鏡像

CI 階段無法阻擋的：
  ❌ 部署 YAML 中的錯誤安全配置
     例：privileged: true（容器以 root 完整權限運行）
     例：hostPath 掛載節點敏感路徑（/etc/passwd）
     例：使用 :latest 標籤（版本不可追溯）
     例：不宣告資源 Limits（可能耗盡節點資源）
  ❌ 開發者有意或無意的特權操作（RBAC 未限制）
```

**集群硬化的防禦定位**：

```
[CI 防禦層] 鏡像安全（Trivy 掃描 + Cosign 簽章）
       │
       ▼
[准入控制層] 部署配置安全（Kyverno Policy + PSA）← 本篇重點
       │
       ▼
[運行期防禦層] 行為監控（Falco）← 見 06 筆記
```

## 二、K8s 請求生命週期（理解防禦的基礎）

要理解「准入控制」發生在哪裡，先看一個 `kubectl apply` 的請求如何被處理：

```
kubectl apply -f pod.yaml
       │
       ▼ HTTPS
  kube-apiserver
       │
       ▼ 【Step 1：Authentication（身份驗證）】
       │    你是誰？（憑證 / ServiceAccount Token / OIDC）
       │
       ▼ 【Step 2：Authorization（授權）】
       │    你被允許做這件事嗎？（RBAC 檢查）
       │
       ▼ 【Step 3：Admission Control（准入控制）】← 本篇核心
       │    這個操作符合安全策略嗎？（Kyverno / PSA）
       │    ├── Mutating Webhook（可修改請求）
       │    └── Validating Webhook（只驗證，不通過則拒絕）
       │
       ▼ 【Step 4：寫入 etcd】
       │    物件持久化儲存
       │
       ▼
  Kubelet 接收並執行
```

## 三、K8s RBAC 最小特權

### 3.1 核心概念與四個資源

RBAC（Role-Based Access Control）透過四種資源的組合，定義「誰能對哪些資源做什麼操作」：

| 資源 | 作用範圍 | 說明 |
|------|---------|------|
| **`Role`** | 單一 Namespace | 定義一組「允許的操作」（不能跨 namespace）|
| **`ClusterRole`** | 整個集群 | 同 Role，但適用所有 namespace 或集群級資源（Node、PV 等）|
| **`RoleBinding`** | 單一 Namespace | 將 Role 或 ClusterRole **綁定**到主體（Subject）|
| **`ClusterRoleBinding`** | 整個集群 | 將 ClusterRole 綁定到主體，效力及於所有 namespace |

**主體（Subject）**——誰能被綁定：
- `User`：真人使用者（透過 kubeconfig 認證）
- `Group`：使用者群組
- `ServiceAccount`：Pod 內部程序的身份（最常用）

### 3.2 RBAC 工作原理

```yaml
# Step 1：定義 Role（允許哪些操作）
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: production         # 只在 production namespace 有效
rules:
  - apiGroups: [""]             # "" 代表核心 API group
    resources: ["pods"]         # 能操作 pods
    verbs: ["get", "list", "watch"]  # 只能讀，不能改/刪
```

```yaml
# Step 2：RoleBinding（把 Role 綁給誰）
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: production
subjects:
  - kind: ServiceAccount
    name: monitoring-agent     # 綁給這個 ServiceAccount
    namespace: monitoring
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

**Verbs（動詞）完整清單**：

| Verb | 對應操作 |
|------|---------|
| `get` | 查詢單一資源 |
| `list` | 列出資源清單 |
| `watch` | 持續監聽資源變化 |
| `create` | 建立新資源 |
| `update` | 更新資源（PUT）|
| `patch` | 部分更新（PATCH）|
| `delete` | 刪除資源 |
| `deletecollection` | 批量刪除 |
| `*` | **萬用（危險！）**|

### 3.3 常見錯誤配置（高風險）

| 錯誤 | 範例 | 風險 |
|------|------|------|
| **Wildcard verb** | `verbs: ["*"]` | 擁有對該資源的完整控制權 |
| **Wildcard resource** | `resources: ["*"]` | 可操作所有資源類型 |
| **cluster-admin 濫用** | 把 `cluster-admin` ClusterRole 綁給應用 SA | 應用程式可以刪除任何資源、讀取所有 Secret |
| **跨 namespace 存取** | ClusterRoleBinding + 廣泛 Role | 一個 namespace 被攻破後橫向移動 |
| **default SA 未限制** | Pod 使用 `default` ServiceAccount | 若 default SA 有多餘權限，任何 Pod 都繼承 |

**實務最佳做法**：

```yaml
# 每個應用建立專屬 ServiceAccount，不使用 default
apiVersion: v1
kind: ServiceAccount
metadata:
  name: myapp-sa
  namespace: production
automountServiceAccountToken: false  # 不需要 API 存取的 Pod，直接關閉 Token 掛載
```

### 3.4 快速審查指令

```bash
# 查看所有 ClusterRoleBinding（找出誰有 cluster-admin）
kubectl get clusterrolebindings -o wide | grep cluster-admin

# 查看特定 ServiceAccount 有哪些權限
kubectl auth can-i --list --as=system:serviceaccount:production:myapp-sa

# 查看某個動作是否被允許
kubectl auth can-i delete pods --as=system:serviceaccount:production:myapp-sa -n production
```

## 四、准入控制器（Admission Controller）

### 4.1 兩種 Webhook 類型

准入控制在 Step 3 分兩個階段執行，順序固定：

```
API 請求
   │
   ▼ 【Mutating Admission Webhook】（可修改請求物件）
   │   先執行：可以在物件被儲存前自動注入欄位
   │   例：Istio 自動注入 Sidecar Container
   │   例：自動加入預設資源 Limits
   │   例：自動加上必要的 Label / Annotation
   │
   ▼ 物件驗證（Schema Validation）
   │
   ▼ 【Validating Admission Webhook】（只驗證，不能修改）
   │   後執行：最終判斷是否允許此操作
   │   例：Kyverno 驗證 Pod 是否使用 :latest 標籤
   │   例：OPA Gatekeeper 驗證 Label 合規性
   │
   ▼ 通過 → 寫入 etcd
   ✗ 不通過 → 回傳錯誤，操作中止
```

| 類型 | 能否修改物件 | 執行順序 | 典型用途 |
|------|-----------|---------|---------|
| **MutatingWebhook** | ✅ 可以 | 先 | 自動注入 Sidecar、補全預設值 |
| **ValidatingWebhook** | ❌ 不行 | 後 | 安全策略驗證、合規檢查 |

## 五、Kyverno 策略引擎

### 5.1 Kyverno vs OPA/Rego

| 面向 | Kyverno | OPA/Rego |
|------|---------|----------|
| **規則語言** | Kubernetes YAML（原生語法）| Rego（專屬 DSL，需學習）|
| **學習曲線** | 低（會寫 K8s YAML 就會）| 高（函數式語言邏輯）|
| **策略類型** | Validate、Mutate、Generate、VerifyImages | 主要是 Validate |
| **社群規則庫** | ✅ Kyverno Policies 開源庫 | 需自己維護 |
| **適合場景** | 中小型團隊、快速導入 | 複雜邏輯、大型企業已有 OPA 生態 |

**結論**：大多數場景 Kyverno 已足夠，且上手成本遠低於 OPA。

### 5.2 核心資源類型

| 資源 | 作用範圍 | 適用場景 |
|------|---------|---------|
| `Policy` | 單一 Namespace | 各團隊自行管理的局部策略 |
| `ClusterPolicy` | 整個集群所有 Namespace | 全集群強制的安全基線（推薦）|

### 5.3 validationFailureAction 模式

| 模式 | 行為 | 適用時機 |
|------|------|---------|
| `Audit` | 記錄違規到 Policy Report，**不阻斷**部署 | 初期觀察，評估影響範圍 |
| `Enforce` | 違規時直接拒絕 API 請求，返回錯誤 | 規則穩定後正式執行 |

**建議上線流程**（避免直接 Enforce 導致生產中斷）：

```
第一週：Audit 模式上線
   │   觀察 Policy Report，找出哪些現有資源違規
   │   kubectl get policyreport -A
   │
   ▼
清理現有違規資源（更新 YAML、補上缺少的設定）
   │
   ▼
切換 Enforce 模式
   │   只改一行：validationFailureAction: Enforce
   │
   ▼
監控部署是否有非預期阻斷，必要時調整規則
```

### 5.4 常用策略範例

#### 策略一：禁止使用 `:latest` 標籤

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-latest-tag
  annotations:
    policies.kyverno.io/title: Disallow Latest Tag
    policies.kyverno.io/description: >-
      Using :latest tag makes deployments non-reproducible. Require explicit version tags.
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: check-image-tag
      match:
        any:
          - resources:
              kinds: [Pod]
      validate:
        message: "Image tag ':latest' is not allowed. Specify an explicit version tag."
        pattern:
          spec:
            containers:
              - image: "!*:latest"   # ! 表示不符合此 pattern 才通過
            =(initContainers):       # = 前綴表示此欄位存在時才驗證
              - image: "!*:latest"
```

**防禦目的**：
- `:latest` 每次 pull 可能拉到不同版本 → 部署不可重現
- 無法確認運行中的版本 → 出問題難以回滾
- CI 掃描是針對特定 digest，`:latest` 部署時可能換了版本

---

#### 策略二：強制宣告資源 Limits

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-resource-limits
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: check-resource-limits
      match:
        any:
          - resources:
              kinds: [Pod]
      validate:
        message: "CPU and Memory limits must be defined for all containers."
        pattern:
          spec:
            containers:
              - resources:
                  limits:
                    memory: "?*"   # ?* 表示該欄位必須存在且非空
                    cpu: "?*"
```

**防禦目的**：
- 沒有 Limits → 單一容器可以耗盡節點的所有 CPU / Memory
- 影響同節點上所有其他 Pod → 連鎖故障
- K8s QoS 等級依賴 Limits 設定（Guaranteed > Burstable > BestEffort）

---

#### 策略三：禁止特權容器

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-privileged-containers
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-privileged
      match:
        any:
          - resources:
              kinds: [Pod]
      validate:
        message: "Privileged containers are not allowed."
        pattern:
          spec:
            containers:
              - =(securityContext):
                  =(privileged): "false"  # 如果欄位存在，值必須是 false
```

**防禦目的**：
- `privileged: true` = 容器幾乎等同於在節點上以 root 運行
- 可突破容器隔離邊界、讀取 `/proc`、掛載設備
- 一旦被攻破 → 整個節點淪陷

---

#### 策略四：禁止 hostPath 掛載

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-host-path
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-hostpath
      match:
        any:
          - resources:
              kinds: [Pod]
      validate:
        message: "HostPath volumes are not allowed. Use PVC instead."
        deny:
          conditions:
            any:
              - key: "{{ request.object.spec.volumes[].hostPath | length(@) }}"
                operator: GreaterThan
                value: 0
```

**防禦目的**：
- `hostPath` 允許容器直接掛載節點的檔案系統路徑
- 攻擊者可以讀取 `/etc/shadow`、`/var/lib/kubelet/pki/` 等敏感路徑
- 或向節點寫入惡意腳本

---

#### 策略五：限制 Registry 來源

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: restrict-image-registries
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-registry
      match:
        any:
          - resources:
              kinds: [Pod]
      validate:
        message: "Images must come from approved registries: 123456789.dkr.ecr.ap-northeast-1.amazonaws.com or gcr.io/myproject"
        pattern:
          spec:
            containers:
              - image: "123456789.dkr.ecr.ap-northeast-1.amazonaws.com/* | gcr.io/myproject/*"
```

**防禦目的**：防止開發者直接從 Docker Hub 拉取未審查的公開鏡像進入生產環境。

## 六、PSA / PSS — K8s 內建的 Pod 安全標準

K8s v1.25+ 後 Pod Security Policy（PSP）已廢棄，改由 **Pod Security Admission（PSA）** 搭配 **Pod Security Standards（PSS）** 取代，且為**內建功能，無需安裝額外工具**。

### 6.1 三個安全等級

| 等級 | 限制程度 | 說明 |
|------|---------|------|
| **Privileged** | 無限制 | 完全開放，等同無策略。僅用於受信任的系統元件 |
| **Baseline** | 基本防護 | 禁止已知高風險設定（privileged、hostNetwork、hostPID 等）|
| **Restricted** | 最嚴格 | 符合 Pod 安全最佳實踐，禁止所有特權操作、要求 non-root |

### 6.2 三種執行模式

| 模式 | 行為 |
|------|------|
| `enforce` | 違規 Pod 直接被拒絕建立 |
| `audit` | 違規會在稽核日誌留下紀錄，但不阻斷 |
| `warn` | 違規會向使用者回傳警告訊息，但不阻斷 |

### 6.3 透過 Namespace Label 啟用

```yaml
# 對 production namespace 啟用 Restricted 等級（enforce + warn + audit 可同時設定）
apiVersion: v1
kind: Namespace
metadata:
  name: production
  labels:
    # 正式阻斷違規 Pod
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: latest

    # 同時記錄稽核日誌
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/audit-version: latest

    # 向開發者顯示警告
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/warn-version: latest
```

### 6.4 PSA vs Kyverno — 什麼時候用哪個？

| | PSA | Kyverno |
|--|-----|---------|
| **安裝需求** | 內建，零安裝 | 需安裝 Kyverno |
| **規則彈性** | 固定三個等級，無法自定義 | 高度自定義 |
| **自動修復（Mutate）** | ❌ | ✅ |
| **適合場景** | 快速設定基本安全基線 | 需要細粒度控制 |

**推薦策略**：**PSA 做基線 + Kyverno 做細粒度控制**，兩者互補。

## 重點概念速查

- **RBAC**：以角色為基礎的存取控制，透過 Role + RoleBinding 定義「誰能對哪些資源做什麼」
- **最小特權原則**：每個 ServiceAccount 只給完成其工作所需的最小權限，不多給一個 verb
- **Admission Controller**：kube-apiserver 的插件，在物件被持久化前進行驗證或修改
- **Mutating Webhook**：先執行，可修改請求物件（如自動注入 Sidecar）
- **Validating Webhook**：後執行，只驗證不修改，不通過則拒絕整個操作
- **Kyverno**：K8s 原生策略引擎，用 YAML 寫規則，支援 Validate / Mutate / Generate
- **`validationFailureAction: Audit`**：觀察模式，記錄但不阻斷，上線初期使用
- **`validationFailureAction: Enforce`**：強制模式，違規直接拒絕部署
- **PSA（Pod Security Admission）**：K8s v1.25+ 內建，透過 Namespace Label 設定安全等級
- **PSS（Pod Security Standards）**：三個預定義安全等級：Privileged / Baseline / Restricted
- **cluster-admin**：K8s 最高權限 ClusterRole，濫用是常見嚴重安全風險
