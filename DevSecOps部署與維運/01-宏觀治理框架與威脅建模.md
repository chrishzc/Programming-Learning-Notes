# 01 · 宏觀治理框架與威脅建模

> **學習目標**：理解 DevSecOps 的理論依據與國際框架，建立「為什麼要做安全」的系統觀，而非直接跳入工具操作。

---

## 學習框架

### 一、為什麼需要宏觀框架？

在缺乏宏觀框架引導的情況下，技術團隊極易落入以下陷阱：

- **工具堆疊無序**：根據當下需求或熱門趨勢盲目採購/部署工具（SAST、DAST、WAF、SIEM...），工具間缺乏協調，各自為政。
- **防禦碎片化**：有些環節過度防禦，有些關鍵環節完全空白，整體安全態勢無從評估。
- **無法量化成效**：無法回答「我們的安全做到什麼程度」，也無法向管理層匯報改善進展。
- **重複修補、不治根本**：每次出事後補一個工具，下次換個角度攻擊又破了。

**宏觀框架的價值**：提供一套以**結果為導向**的標準，讓團隊知道「該做哪些事、做到什麼程度、如何驗證已做到」，而不是被工具廠商牽著走。

> 💡 框架不是工具清單，而是**思考安全的結構化方法**。

### 二、NIST SP 800-218 安全軟體開發框架（SSDF）

由美國國家標準暨技術研究院（NIST）制定，是目前國際最具權威的 DevSecOps 治理綱領。SSDF 的重要特性：

- **技術中立**：不綁定特定工具或雲端平台
- **結果導向**：以「達到的安全結果」定義標準，而非規定「必須用哪個工具」
- **可映射至 CI/CD**：四大板塊可直接對應到開發生命週期的各個階段

#### 2.1 四大板塊概覽

| 板塊     | 縮寫  | 核心目標         | 對應生命週期階段 |
| ------ | --- | ------------ | -------- |
| 準備組織   | PO  | 建立安全開發的組織基礎  | 規劃前期     |
| 保護軟體   | PS  | 確保程式碼與產物完整性  | 開發、構建、發布 |
| 生產安全軟體 | PW  | 主動消除軟體中的漏洞   | 開發、測試    |
| 響應漏洞   | RV  | 建立上線後的閉環修補機制 | 維運、監控    |

#### 2.2 PO — 準備組織（Prepare the Organization）

**核心問題**：在寫第一行代碼之前，組織做好安全開發的準備了嗎？

**關鍵實踐**：

- **定義角色與職責**：誰負責安全需求定義？誰負責代碼審查？誰負責漏洞響應？角色模糊是安全失效的首因。
- **制定統一安全政策**：包括密碼政策、機敏資訊處理規範、第三方依賴引入標準等，形成書面文件。
- **建立工具鏈與環境支持**：為開發人員提供安全測試工具（IDE 插件、pre-commit hooks），降低「安全」的使用門檻。
- **安全培訓**：確保開發人員理解 OWASP Top 10 等基礎漏洞，安全不應只是安全團隊的責任。
#####  ==OWASP Top 10==

| **排名**  | **風險項目 (English / 中文)**                                   | **簡介與常見情境**                                                                                           |
| ------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **A01** | **Broken Access Control**<br><br>權限控制失效                   | ==系統未正確限制使用者的權限==。攻擊者可透過修改網址、參數或 API 請求（如把 `user_id=101` 改為 `102`），直接存取或修改別人的私密資料。（_註：原 SSRF 已併入此類別_） |
| **A02** | **Security Misconfiguration**<br><br>安全設定錯誤               | ==系統、雲端服務或伺服器組態設定不當==。例如使用預設密碼、開啟不必要的服務埠、開啟 Debug 模式導致洩漏敏感資訊，或雲端儲存桶（S3 Bucket）未設限公開。                  |
| **A03** | **Software Supply Chain Failures**<br><br>軟體供應鏈失敗         | ==軟體建置、發布與依賴庫管理過程中的破綻==。例如使用了含有已知漏洞的開源套件（如 npm/NuGet）、CI/CD 自動化管道被植入惡意程式碼，或遭毒化套件（Typosquatting）攻擊。    |
| **A04** | **Cryptographic Failures**<br><br>密碼學失敗                   | 敏感資料（如密碼、信用卡、個人身分資訊）在傳輸或儲存時未加密，或使用了過時、強度不足的演算法（如 MD5/SHA1），導致資料容易遭竊取或解密。                              |
| **A05** | **Injection**<br><br>注入攻擊                                 | 包含 **SQL 注入（SQLi）**、**XSS（跨網站指令碼）** 與 Command Injection。==未經過濾的外部輸入被當成系統指令執行==，導致資料庫被翻陸、權限被竊取或網站被篡改。  |
| **A06** | **Insecure Design**<br><br>不安全設計                          | 系統在架構與業務邏輯設計階段就存在固有缺陷。這不是程式碼寫錯（Bug），而是==缺乏安全防護設計==（如未設計防止搶購機器人的機制、無密碼爆破防禦架構）。                         |
| **A07** | **Authentication Failures**<br><br>身份驗證失敗                 | ==身分驗證機制存在漏洞==。常見情境包含：允許弱密碼、未防止憑證填充（Credential Stuffing）攻擊、二階段驗證（MFA）可被繞過，或 Session token 管理不當。       |
| **A08** | **Software or Data Integrity Failures**<br><br>軟體或資料完整性失敗 | ==系統使用了未經簽章驗證的軟體更新、跨網域資料交換沒有進行完整性檢查，或是反序列化漏洞（Deserialization）==，讓攻擊者能竄改關鍵資料或執行惡意碼。                    |
| **A09** | **Security Logging & Alerting Failures**<br><br>安全紀錄與警報失敗 | ==系統缺少足夠的安全日誌（Log）紀錄，或是缺乏**即時警報（Alerting）機制**==。導致攻擊者入侵數月甚至數年，企業都毫無察覺。                                |
| **A10** | **Mishandling of Exceptional Conditions**<br><br>異常情況處理不當 | ==系統在遇到非預期錯誤、例外狀況或極端邊界條件時處理不當==。常見如「預設放行（Fail-Open）」邏輯，當驗證伺服器連不上時直接允許過關，或回傳完整的 Error Trace 洩漏內部架構資訊。  |
|         |                                                           |                                                                                                       |
> **一句話記憶**：PO = 人、制度、工具三者就位。

#### 2.3 PS — 保護軟體（Protect the Software）

**核心問題**：如何確保程式碼、依賴項、構建產物在整個生命週期中未被篡改？

**關鍵實踐**：

- **原始碼存取控制**：版本控制系統（Git）的分支保護、最小化 commit 權限、強制 PR Review。
- **構建產物完整性驗證**：
  - 對 Container Image 進行數位簽章（如 Cosign + Sigstore），確保 Registry 中的鏡像是「真品」
  - 生成並驗證 SBOM（軟體物料清單），追蹤所有直接/間接依賴的來源
- **防範供應鏈投毒**：
  - 依賴項釘定版本（Pin dependencies）
  - 使用私有/可信 Artifact Registry，而非直接拉取公共源
  - 驗證第三方依賴的簽章與雜湊

> **一句話記憶**：PS = 軟體從寫入到發布的完整性保護鏈。

#### 2.4 PW — 生產安全軟體（Produce Well-Secured Software）

**核心問題**：如何在軟體構建與發布**之前**，主動找出並消除漏洞？

**關鍵實踐**：

- **安全編碼實踐**：遵循 OWASP 安全編碼規範，避免注入攻擊、認證缺陷等基礎漏洞。
- **自動化代碼審查（SAST）**：在 CI 管道中執行靜態應用安全測試，於合併代碼前攔截已知漏洞模式。
- **第三方依賴合規驗證（SCA）**：自動掃描依賴項的已知 CVE，並驗證授權條款合規性。
- **機敏資訊掃描**：防止 API Key、密碼等機敏資訊被意外提交到版本庫（gitleaks、truffleHog）。
- **威脅建模（Threat Modeling）**：在設計階段主動分析攻擊面（詳見第三節）。

> **一句話記憶**：PW = 「讓有漏洞的代碼根本進不了生產環境」。

#### 2.5 RV — 響應漏洞（Respond to Vulnerabilities）

**核心問題**：系統上線運行後發現新漏洞時，如何迅速、有序地應對？

**關鍵實踐**：

- **建立漏洞接收管道**：公開的安全揭露信箱（Security Disclosure Policy）、CVE 訂閱通知。
- **漏洞分類與優先排序**：依 CVSS 評分、可利用性、業務影響進行分流（詳見 [06 筆記](./06-漏洞分流ASPM與度量指標.md)）。
- **快速修補與發布流程**：安全修補不應走一般功能發布的漫長流程，需有緊急發布通道。
- **根因分析（Root Cause Analysis）**：修完漏洞後，回溯「為什麼這個漏洞能進入生產」，修補流程缺口。
- **虛擬補丁（Virtual Patching）**：在代碼修復完成前，先以 WAF 規則阻斷已知攻擊向量（詳見 [03 筆記](./03-WAF-as-Code實踐.md)）。

> **一句話記憶**：RV = 「發現漏洞後不慌亂，有標準流程快速閉環」。

### 三、威脅建模

#### 3.1 什麼是威脅建模，何時做？

**威脅建模（Threat Modeling）** 是一種結構化的安全分析方法，目的是在系統**設計階段**就系統化識別潛在的安全威脅，並在寫代碼之前決定如何應對。

**為什麼要在設計階段做？**

| 修復時機 | 相對成本 |
|---------|---------|
| 需求 / 設計階段 | 1x（改一個設計決策）|
| 開發階段 | 6x（改代碼、補測試）|
| 測試階段 | 15x（重設計、重測試）|
| 生產上線後 | 100x+（緊急補丁、潛在損失、商譽傷害）|

**何時做？**

- ✅ 新功能或服務設計之初
- ✅ 架構有重大變更時（如從單體轉微服務）
- ✅ 引入新的外部整合（第三方 API、支付系統等）
- ✅ 定期複審（建議每季或每次重大發版前）

**四個核心問題**（微軟威脅建模框架）：

1. 我們在構建什麼？（系統描述）
2. 哪裡可能出問題？（威脅識別）
3. 我們要怎麼因應？（緩解措施）
4. 我們做得夠好嗎？（驗證）

#### 3.2 STRIDE 模型

STRIDE 是微軟提出的威脅分類框架，對應六類攻擊類型，每類都有對應的安全屬性（即需要保護的東西）：

| 字母    | 威脅類型                         | 破壞的安全屬性                | 具體範例                          |
| ----- | ---------------------------- | ---------------------- | ----------------------------- |
| **S** | Spoofing（仿冒）                 | 身份驗證（Authentication）   | 攻擊者偽造 JWT Token、假冒合法用戶登入      |
| **T** | Tampering（篡改）                | 完整性（Integrity）         | 中間人攻擊修改 API 回應、篡改資料庫記錄        |
| **R** | Repudiation（抵賴）              | 不可否認性（Non-repudiation） | 惡意用戶執行刪除操作後聲稱未做，缺乏稽核日誌無法反駁    |
| **I** | Information Disclosure（資訊洩露） | 保密性（Confidentiality）   | 錯誤訊息洩漏 Stack Trace、目錄遍歷讀取系統檔案 |
| **D** | Denial of Service（拒絕服務）      | 可用性（Availability）      | 大量請求耗盡資源、慢速連接攻擊（Slowloris）    |
| **E** | Elevation of Privilege（特權提升） | 授權（Authorization）      | 一般用戶透過參數篡改存取管理員功能（IDOR）       |

#### 3.3 實作步驟（如何對一個系統做威脅建模）

以一個典型的「用戶登入 API」為例，示範五步驟流程：

**Step 1 · 畫出系統資料流圖（DFD, Data Flow Diagram）**

識別系統中的所有元件與資料流向：
- **外部實體（External Entity）**：使用者瀏覽器、外部 API
- **處理程序（Process）**：Auth Service、Token Service
- **資料存儲（Data Store）**：User DB、Session Cache
- **資料流（Data Flow）**：連接各元件的箭頭，標注傳輸的資料與協定
- **信任邊界（Trust Boundary）**：用虛線圈出「信任等級不同的區域」，如公網 vs 內網

**Step 2 · 針對每條資料流與元件套用 STRIDE**

逐一問：「這個元件/資料流，在 STRIDE 的六個維度上，哪裡可能出問題？」

```
範例：/api/auth/login 端點
- S（仿冒）：攻擊者用別人的帳密暴力破解？ → 速率限制、MFA
- T（篡改）：傳輸中的憑證被修改？ → 強制 HTTPS/TLS
- I（洩露）：登入失敗訊息是否洩漏「帳號是否存在」？ → 統一回傳模糊訊息
- D（DoS） ：大量登入請求打爆 DB？ → 限流 + 帳號鎖定機制
```

**Step 3 · 評估風險（風險 = 可能性 × 衝擊）**

使用 DREAD 或 CVSS 給每個威脅評分，決定優先處理順序。

**Step 4 · 制定緩解措施**

| 威脅 | 緩解措施 | 實作方式 |
|------|---------|---------|
| 暴力破解（S）| 速率限制 + MFA | Nginx limit_req、TOTP |
| Token 偽造（S/T）| 強簽章 + 短效期 | JWT + RS256、Refresh Token Rotation |
| 資訊洩漏（I）| 統一錯誤回應 | 代碼層統一 Error Handler |

**Step 5 · 驗證與追蹤**

- 將威脅建模產出寫入 ADR（架構決策記錄）或安全需求 Issue
- 在 CI 的安全測試中，加入針對上述威脅的自動化測試案例

##### 補充
CVSS 會根據漏洞的物理與技術特徵，計算出一個 **0.0 到 10.0 分** 的分數：

| **分數範圍**       | **嚴重程度等級 (Severity)** | **代表意義**                                      |
| -------------- | --------------------- | --------------------------------------------- |
| **0.0**        | None (無)              | 無安全性影響                                        |
| **0.1 - 3.9**  | Low (低)               | 難以利用、影響極小                                     |
| **4.0 - 6.9**  | Medium (中)            | 需要特定條件才能利用，影響有限                               |
| **7.0 - 8.9**  | High (高)              | 容易被利用，可能導致資料洩漏或系統部分癱瘓                         |
| **9.0 - 10.0** | Critical (超高)         | 極度危險，遠端即可輕鬆攻陷，影響範圍極大（如 Log4Shell、WannaCry 漏洞） |

**DREAD** 是微軟開發的一套評分模型，名字來自於其評分的 **5 個核心維度字母縮寫**。它的設計目的是讓開發與資安團隊在進行「威脅建模」時，能快速排出修復漏洞的優先順序

|**字母**|**英文項目**|**中文解釋**|**評估問題**|
|---|---|---|---|
|**D**|**Damage Potential**|傷害潛力|如果這個漏洞被成功利用，會造成多大的破壞與損失？|
|**R**|**Reproducibility**|重現性|成功觸發或重複執行這個攻擊的難易度高嗎？是每次都能成功，還是偶爾才行？|
|**E**|**Exploitability**|可利用性|攻擊者需要多少技術門檻與工具？是菜鳥隨手能下指令，還需要專家寫程式？|
|**A**|**Affected Users**|受影響使用者|系統中會有多少比例的使用者（或資產）受到這個漏洞影響？|
|**D**|**Discoverability**|可發現性|這個漏洞有多容易被攻擊者發現？（是直接暴露在網頁上，還是藏在極深的邏輯裡？）|

==DREAD vs. CVSS 比較總結==

|**特性**|**DREAD**|**CVSS**|
|---|---|---|
|**主要用途**|軟體開發內部、威脅建模 (Threat Modeling)|國際通用漏洞公告 (CVE)、資安通報、合規稽核|
|**主觀/客觀度**|**較主觀**（依據團隊經驗與企業情境評分）|**極客觀**（有嚴謹且固定的公式與評估標準）|
|**優點**|簡單直覺，適合開發團隊快速溝通優先順序|國際統一標準，任何資安人員看懂分數就知道嚴重性|
|**缺點**|不同人評分結果差異大，難以標準化|公式較複雜，手動計算較繁瑣

```
┌──────────────────────────────────────────────┐
│  運行期監控（持續保護）                        │
│                                              │
│  WAF 阻斷 L7 攻擊（虛擬補丁）                │  ← RV
│  Falco 異常行為偵測                           │  ← RV
│  CVE 訂閱通知 ──→ 漏洞分流 ──→ 修補發布       │  ← RV
│  MTTD / MTTR 指標追蹤                        │  ← RV
└──────────────────────────────────────────────┘
```

**SSDF 板塊與 CI/CD 階段對應總結**：

| SSDF 板塊 | 主要落地位置 | 代表工具/實踐 |
|---------|------------|-------------|
| PO（準備組織）| 全程（制度層）| 分支保護策略、安全培訓、安全政策文件 |
| PS（保護軟體）| 構建、發布階段 | Cosign 簽章、SBOM、私有 Registry |
| PW（生產安全軟體）| 開發、CI、測試階段 | SAST、SCA、機敏掃描、DAST、Kyverno |
| RV（響應漏洞）| 運行期 | WAF 虛擬補丁、Falco、ASPM、MTTR 追蹤 |

## 重點概念速查

- **安全左移（Shift-Left）**：==將安全檢測從「上線前最後一道關卡」移到「開發、設計的最早期」==，修復成本最低、效果最好。
- **持續運行期保護**：==軟體上線後安全工作不停止==，WAF、Falco、漏洞監控構成持續防禦層，對應 SSDF 的 RV 板塊。
- **供應鏈安全**：==現代軟體 80%+ 的代碼來自第三方依賴==，攻擊者轉而攻擊「上游組件」（如 npm 套件投毒），需透過 SCA、SBOM、Cosign 簽章保護。
- **SSDF**：NIST 發布的安全軟體開發框架，技術中立、結果導向，是 DevSecOps 的國際標準治理綱領。
- **STRIDE**：微軟威脅建模框架，六類威脅：仿冒、篡改、抵賴、資訊洩露、拒絕服務、特權提升。
- **信任邊界（Trust Boundary）**：系統中信任等級不同的區域分界線，是威脅建模時最需要仔細審查的位置。
- **DFD（資料流圖）**：威脅建模的主要視覺化工具，描繪系統中資料如何在各元件間流動。
