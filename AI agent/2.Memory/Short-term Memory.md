# 短期記憶 (Short-term Memory)

> [!ABSTRACT]
> 探討短期記憶在上下文視窗中的作用與限制、上下文膨脹面臨的挑戰，以及利用 MCP 代碼模式與子代理人隔離來進行優化的現代策略。

---

## 一、 短期記憶的角色與機制

**短期記憶（Short-term Memory）** 主要是透過大型語言模型的**上下文視窗（Context Window）** 來實現的。在代理人架構中，記憶組件被分為短期與長期兩部分。短期記憶被視為代理人的即時工作空間：

- **實現機制**：短期記憶==完全依賴於模型有限的上下文視窗長度==。
- **功能**：它主要用於**存儲和操縱與當前任務直接相關的即時資訊**。這使代理人能夠理解並適應給定的語境，保留當前任務的關鍵細節。
- **在線學習（In-context Learning）**：研究者將所有的「在線學習」視為利用模型的短期記憶來學習新資訊的過程。==利用ReAct反思機制在同一個context中學習如何較好的完成當前任務==
    - **Few-shot Prompting**：藉由在提示詞中提供 1 到 2 個正確完成任務的範例，引導模型在當前任務中表現得更好，但離開當前context後，範例隨即消失，效果無法持久。

## 二、 物理限制與工程挑戰

雖然短期記憶對於即時推理至關重要，但它在工程實踐中面臨嚴重的物理限制：

- **資源過載**：工具的定義（Tool Definitions）和中間執行結果會迅速填滿上下文視窗。當連接數百或數千個工具時，代理人在讀取用戶請求前可能就已經消耗了數十萬個 Token。
- **成本與延遲**：過多的中間結果（如大型會議記錄或數據結構）在每一輪對話中反覆傳遞，會顯著增加 API 成本並導致回應延遲。
- **推理錯誤**：當上下文包含過多大數據量或複雜結構時，模型在不同工具調用之間複製數據時更容易出錯。
- **邏輯干擾與分心**：子代理人若未進行上下文隔離，會被主代理人累積的雜亂歷史資訊（噪音）所干擾，進而失去對當前細分任務的專注力。
- **破壞工作流**：當處理的大型文件或中間結果超過模型物理上的上下文視窗限制（Context Window Limit）時，執行鏈條會直接中斷導致任務失敗。

## 三、 優化架構：MCP 與代碼模式

為了更有效地管理短期記憶空間（即上下文視窗），[[MCP Client & MCP Server|MCP]] 透過「代碼模式（[[code 模式|Code Mode]]）」改進上下文效率。代理人不再將所有中間結果傳回模型，而是在沙箱環境中直接處理數據：

- **精簡資訊流**：LLM 撰寫腳本，在隔離的沙箱中對原始數據進行計算與過濾，僅將精煉後的結果回傳模型。
- **顯著節省**：透過這種方式，原本需要 15 萬個 Token 的任務可以縮減至 2,000 個，**節省高達 98.7% 的空間與成本**。

## 四、 優化架構：子代理人與上下文隔離

當任務涉及多步驟推理或產生大量噪音時，將任務分配給擁有**獨立上下文視窗**的子代理人（[[AI Agent 概論|Subagents]]）是更優的做法：

- **上下文隔離（Context Isolation）**：子代理人可以在乾淨的環境中運作，不受主代理人累積歷史的干擾，從而提高輸出的連貫性與準確度。
- **維持主大腦的決策精準度**：子代理人在背景完成繁複的推理後，==只傳送該次任務所需的最終結果給主代理人==，使主代理人的上下文始終保持精簡。

## 五、 短期記憶與長期記憶的協作

在完整的記憶系統中，短期記憶與[[Long-term Memory|長期記憶]]相輔相成：

- **短期記憶（Context）**：用於當前對話、即時任務與細微的語意理解。
- **長期記憶（Long-term Memory）**：通常利用外部的**向量數據庫（[[RAG|Vector Store]]）**實現，提供跨對話、跨部署召回海量歷史資訊的能力。

**總結來說**，短期記憶是代理人進行即時決策與推理的工作記憶空間，但由於其物理空間有限且昂貴，在實作 Agent 時，不能只是讓對話歷史無限延長。你需要建立一套 **「資訊生命週期管理」**機制：

1. **即時資訊**：留在 Context Window（短期記憶）中。
2. **成功經驗**：儲存為 Skills（工具箱）。
3. **海量事實**：存入 Vector DB（長期記憶）。
4. **中間過程**：==資訊與推理過程在沙箱中處理並「壓縮」為摘要後再回傳模型==
