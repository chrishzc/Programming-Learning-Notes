# 檢索增強生成 (Retrieval-Augmented Generation)

> [!ABSTRACT]
> 說明檢索增強生成 (RAG) 的運作原理、它與 SQL 查詢的本質差異、代理人化 RAG (Agentic RAG/Tool-RAG) 的優化與防禦機制，以及實務中的數據分塊與方案選型。

---

## 一、 RAG 的核心定義與運作原理

**RAG (Retrieval-Augmented Generation)** 是一種結合「資訊檢索」與「內容生成」的技術架構。其核心目的是作為模型的「外部大腦/[[Long-term Memory|長期記憶]]」，克服 [[生成式 AI、LLM 概論|LLM]] 的知識凍結（Frozen Knowledge）限制。它讓模型在生成回應前，先翻閱外部權威知識庫（小抄），確保回答的事實準確度。

### 經典 RAG 的四部曲工作流

在標準的自動化 Data Pipeline 中，經典 RAG 遵循以下確定性流程：

- **分塊 (Chunking)**：將巨量文本（PDF、合約、交易日誌）拆解成具備獨立語意的小片段。
    
- **嵌入 (Embedding)**：透過 Embedding 模型將文字轉化為高維度的「語意向量」。
    
- **向量檢索 (Vector Search)**：將使用者提問也向量化，在向量資料庫中計算**餘弦相似度（Cosine Similarity）**，撈出最接近的文字片段。
    
- **重排序 (Reranking)**：對初步撈出的片段進行精確度評估，精選最相關的內容，剔除上下文噪音。
    

## 二、 核心進化：RAG 與傳統資料庫查詢（SQL）的本質差異

在設計 AI Agent 時，必須釐清這兩種查詢動作在**大腦認知與生命週期**中的不同意義：

|**維度**|**RAG (知識型檢索)**|**傳統資料庫查詢 (精準型操作)**|
|---|---|---|
|**Agent 的本質目的**|**「我想了解這個概念/脈絡，幫我整理」**<br><br>  <br><br>（補足大腦的知識盲區）|**「我想獲取或變更這筆確切的數字/狀態」**<br><br>  <br><br>（精準的商務邏輯執行）|
|**處理的資料類型**|模糊、非結構化（Obsidian 筆記、策略文章、會議紀錄）。|結構化、絕對精確（K 線價格、帳戶餘額、訂單狀態）。|
|**檢索機制**|**語意搜尋（Semantic Search）**。<br><br>  <br><br>算向量距離，重視概念的相似性。|**條件比對（Exact Match）**。<br><br>  <br><br>精準 SQL 比對，容不得半點模糊。|
|**生命週期階段**|**思考與決策階段 (Reasoning)** 的燃料。<br><br>  <br><br>負責「搞懂規則、翻閱說明書」。|**行動與觀察階段 (Action/Observation)** 的工具。<br><br>  <br><br>負責「獲取真實環境狀態（Ground Truth）」。|

## 三、 進階架構：代理人化 RAG (Agentic RAG) 與工具檢索 (Tool-RAG)

當 AI 系統從「單一問答管線」演進為「自主 AI Agent」時，RAG 的實作方式會發生重大的維度改變。

### 前置閘門：意圖過濾 ([[Intent Filtering|Intent Filtering]])

**意圖過濾不等於 RAG**。它是系統的「分診台（Router）」。

- **運作**：在進入 RAG 之前，先透過輕量規則或 Local 小模型（如 Qwen/Llama）判斷使用者意圖。如果是閒聊，直接由大腦回應；如果是問知識，才觸發 RAG 檢索。這能最大化**節省 Token 成本與降低 Latency（延遲）**。
    

### 終極優化：將工具搜尋納入 RAG（Tool-RAG）

當你的交易系統或自動化管線擁有超過 30~50 個工具（APIs）時，把所有工具規格塞給 LLM 會導致 **Token 爆炸**與**模型選擇障礙（Lost in the Middle）**。

- **實作機制**：
    
    1. 將這 50 個「工具的 JSON 規格與描述」存入向量資料庫。
        
    2. 使用者提問時，**先用 RAG 搜尋工具庫**，動態篩選出最相關的 2~3 個工具。
        
    3. 僅將這 2~3 個工具注入給主 LLM，實現動態工具呼叫（Dynamic Tool Use）。
        

### 防禦機制：如果 RAG 沒有檢索到適合的工具？

預設的向量資料庫一定會強制回傳「最接近但實際上完全不相關」的工具，這會導致核心 LLM 瞎呼叫。必須設計以下防禦架構：

- **相似度分數門檻（Similarity Score Threshold）**：設定嚴格的閘門（例如相似度必須 $> 0.70$）。低於門檻，則回傳空清單，代表「查無此工具」。
    
- **降級策略（Fallback）**：當工具箱清空時，系統攔截並降級為「純文本解釋模式」或「萬用兜底工具（Catch-all Tool）」，引導使用者回到正確對話。
    

## 四、 資料分塊（Chunking）與向量存儲實務

### 分塊（Chunking）的核心原則

分塊是建構 RAG 系統的第一步，核心目標是**平衡「語意完整性」與「精確檢索」**。

- **固定長度與重疊（Overlap）**：例如每 500 字一塊，並保留 10%（50 字）的重複重疊，確保語意在切割邊界不被打斷。
    
- **結構化切割**：優先根據文件的自然結構（Markdown 的標題、段落）進行分塊，這通常能保留最完美的上下文語意。
    

### 向量數據庫（Vector DB）方案與選型

- **主流方案**：**Qdrant**（具備極佳的穩定性與大規模檢索效能，常作為標準管線首選）、Milvus、Chroma。
    
- **儲存屬性分流**：
    
    - **文檔事實 (Document Chunks)**：存放量化策略文檔、FAQ，用於知識問答。
        
    - **工具目錄 (Tool Registry)**：存放工具描述（Tool-RAG），用於優化大模型呼叫效率。
        
- **安全與效率**：對於敏感數據（如交易密鑰或財務隱私），可選擇**本地部署（Local Deployment）**，並配合 Docker 沙箱環境運行（如 [[MCP Client & MCP Server|MCP]] 模式中的代碼隔離執行）。
    

## 五、 RAG 的優點與核心侷限

### 👍 核心優點

1. **顯著減少幻覺 (Reduced Hallucinations)**：強迫模型「看著證據說話」，提高商業應用的安全邊界。
    
2. **極高成本效益**：無需花費高昂代價去重新訓練（Retrain）或微調（Fine-Tuning）模型，即可動態更新企業知識庫。
    
3. **具備可追溯性 (Provenance)**：回應時可附帶引用來源（如：_資料來源：策略文件第3頁_），建立人機信任。
