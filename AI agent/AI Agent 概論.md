# AI Agent 概論

> [!ABSTRACT]
> 本章介紹自主 AI Agent 的三大理論支柱（規劃、記憶與工具調用），並說明代理人系統的一步一步設置流程、安全隔離與強健容錯等關鍵開發注意事項。

---

在開始設置前，必須理解代理人的三大支柱：

## 一、 **規劃 (Planning)**：

1. [[2.Subgoal Management|任務拆解]]在規劃中的角色

在自主代理人架構中，規劃被視為代理人的「大腦」功能之一。由於複雜任務通常涉及許多步驟，代理人必須具備預先規劃並理解這些步驟的能力。**任務拆解**正是實現這一點的機制，它讓代理人不再試圖一次性解決整個難題，而是專注於逐個擊破細分的環節。

2. 基於 [[1.ReAct|ReAct]] 框架的動態拆解

- **思維軌跡 (Thought Traces)**：代理人利用自由形式的「思考」步驟來拆解問題、提取資訊並引導下一步的搜尋策略。
- **思考與行動的交織**：透過「思考-行動-觀察 (Thought-Action-Observation)」的循環，代理人可以動態地創建、維持並調整行動計畫。
- **優勢**：僅具備「行動」能力的模型往往無法正確將總目標拆解為子目標；而 ReAct 則利用推理能力精確定位下一步所需的資訊，並根據觀察結果即時修正拆解路徑。

3. 透過子代理人（Subagents）進行拆解

當任務過於複雜或包含相互依賴的非直觀中間步驟時，架構上會採用「子代理人」模式來進行物理層面的任務拆解：

- **委派機制**：編排代理人（Orchestrator）會將具體的、自成一體的子任務發送給專門的子代理人。
- **上下文隔離**：將拆解後的子任務交由子代理人處理，可以防止大量的中間推理過程（噪音）充斥主代理人的上下文視窗，維持主決策鏈的清晰。
- **並行處理**：拆解後的子任務如果彼此獨立，可以交給多個子代理人並行執行，從而提高效率。

4. 任務拆解的具體應用範例

在處理多步驟任務時，任務拆解的過程如下：

- **情境**：查詢特定人物的伴侶年齡並進行數學運算。
- **拆解邏輯**：代理人首先思考其策略——1. 找出伴侶是誰；2. 獲取年齡；3. 執行計算。
- **執行**：每完成一個拆解出的子目標，代理人都會更新其「思考」並決定下一個要處理的細分任務，直到達成最終解答。

5. 為什麼拆解至關重要？

- **克服物理限制**：純粹的多步驟推理若缺乏拆解與外部工具支持，容易產生錯誤累積（Error Propagation）或事實幻覺。
- **提高成功率**：在 ALFWorld 與 WebShop 等決策測試中，具備良好拆解與規劃能力的 ReAct 代理人，其成功率顯著超越了傳統的強化學習與僅具備行動能力的模式。
- **維持可觀測性**：結構化的拆解過程（如 JSON 提示詞）能讓開發者更精確地追蹤代理人在哪個具體環節出現邏輯偏差。
## 二、 **記憶 (Memory)**：分為利用上下文視窗的**[[Short-term Memory|短期記憶]]**，以及利用向量數據庫（[[RAG|Vector Store]]）實現的**[[Long-term Memory|長期記憶]]**。
## 三、 **工具調用 (Tool Use)**：代理人學會調用外部 API（如搜尋、計算器）以獲取模型預訓練權重之外的即時資訊。

---


根據來源提供的實踐指南，設置流程如下：

步驟 1：定義目標與任務

明確定義代理人需要完成的具體任務（如：客戶諮詢、資料分析或內容創作）。清晰的目標有助於後續的配置與工具選擇。

步驟 2：選擇模型與平台

- **模型選擇**：建議使用推理能力強的模型（如 GPT-4 或 Claude 3.5 Sonnet），因為它們對程式概念與邏輯規劃的理解較佳。
- **平台選擇**：可選擇 no-code 平台快速原型設計，或使用 [[Key Frameworks & Protocols|LangChain]]、CrewAI、AutoGen 等框架進行深度開發。

步驟 3：定義與整合工具

代理人並不直接執行功能，而是輸出結構化的 **JSON 請求**。

- 使用 **JSON Schema** 描述工具的名稱、功能與參數。
- **高品質的工具描述**至關重要；如果描述模糊，模型可能無法正確識別何時該調用工具。

步驟 4：建立運行迴圈（Loop）與協定

這是將「[[生成式 AI、LLM 概論|LLM]] + 工具」轉化為「代理人」的關鍵。最常用的理論框架是 **ReAct**：

- **思考 (Thought)**：模型先生成推理軌跡，規劃下一步。
- **行動 (Action)**：模型輸出工具調用指令。
- **觀察 (Observation)**：執行器執行工具並將結果回傳給模型作為「新事實」。
- 重複此過程直到任務完成。

步驟 5：測試、微調與部署

利用內建工具進行測試，並根據反饋調整提示詞（Prompts）與參數。部署後需持續監控性能，防止產生幻覺或陷入死循環。

---


1. 安全隔離與權限控管

- **執行環境隔離**：若允許代理人生成並執行程式碼，必須使用 **Docker 容器**或受限的沙箱（Sandbox）進行物理隔離，以防惡意代碼危害宿主機。
- **人類在環 (Human-in-the-Loop)**：對於涉及金錢、數據刪除或發送訊息等具備破壞性的操作，必須設置人工審批。

2. 防止「工具過載」與「過度工程」

- **工具 vs. 子代理人**：不要一開始就建立複雜架構。如果任務是確定的計算，寫成工具即可；如果需要多步推理，才考慮建立**子代理人（Subagents）**。
- **工具數量限制**：當工具過多時，模型決策準確度會下降。此時可考慮使用 **MCP（[[MCP Client & MCP Server|Model Context Protocol]]）** 標準來精簡上下文並提高效率。

3. 強健的容錯機制

- **錯誤回饋**：當工具執行失敗時，應將錯誤訊息回傳給模型，引導它在下一個思考步驟中修正策略，而非讓系統直接崩潰。
- **資源約束**：必須設置**最大迭代次數（max_iterations）**，防止模型因解析錯誤或無窮路徑而陷入無限迴圈，造成 Token 浪費。

4. 可觀測性 (Observability)

代理人的運行是多步驟且非線性的。記錄完整的「請求 → 思考 → 調用 → 結果 → 回應」日誌是除錯與優化的唯一途徑。
