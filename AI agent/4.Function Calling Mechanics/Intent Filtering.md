# 意圖過濾與模型級聯 (Intent Filtering & Model Cascading)

> [!ABSTRACT]
> 比較意圖過濾與 Tool Choice Model 的顆粒度差異，探討原生 API 的 tool_choice 參數設定，並說明模型級聯 (Model Cascading) 降低 Token 成本的運作機制。

---

### 意圖過濾 (Intent Filtering) ── 粗顆粒度分類

- **任務**：把使用者的話分類到某個「大方向/水管」。
    
- **輸出結果**：它通常只輸出一個簡單的文字標籤或類別（Category）。
    
- **範例**：
    
    - 使用者說：_「幫我看看 BTC 的 RSI 指標。」_
        
    - 意圖過濾器說：`"Intent: market_analysis"`（大方向抓對了，接下來把請求丟給分析管線）。
        

### Tool Choice Model ── 細顆粒度精準控制

- **任務**：不僅要看大方向，還要精確到「勾選出要呼叫哪幾個具體的 Function，連參數格式都準備好」。
    
- **輸出結果**：它不輸出類別標籤，而是直接輸出符合 **JSON Schema Interface** 的 [[Function Calling timing|Function Calling]] 字串。
    
- **範例**：
    
    - 使用者說：_「幫我看看 BTC 的 RSI 指標。」_
        
    - Tool Choice Model 說：`{"name": "query_rsi", "arguments": {"symbol": "BTC"}}`。
        

## 一、 為什麼現代架構會把這兩個詞混著用

在實際工程上，**「意圖過濾」往往就是透過一個「Tool Choice Model」來實作的**。

例如在你之前接觸的系統中，如果你想做意圖過濾，最聰明、最省 Token 的做法，就是丟給 local 的小模型（Llama/Qwen），並把你的「意圖們」包裝成工具：

- 工具 A：`chat_with_user`（當使用者想閒聊時呼叫）
    
- 工具 B：`trigger_rag_pipeline`（當使用者問知識時呼叫）
    
- 工具 C：`execute_trading_flow`（當使用者想下單時呼叫）
    

當小模型在做 **Tool Choice**（選擇呼叫哪一個工具）的時候，它在宏觀架構上，就完美完成了 **意圖過濾** 的工作。

## 二、 在 OpenAI / Gemini API 中的原生「Tool Choice 參數」

除了架構上的獨立模型，在開發呼叫 OpenAI 或 Gemini 的 API 時，參數裡也有一個欄位叫 `tool_choice`。這代表你可以**強制命令模型如何對待工具**：

Python

```
response = client.chat.completions.create(
    model="gpt-4o-mini",
    tools=my_tools,
    tool_choice="auto" # 讓模型自己決定要不要用工具
)
```

在原生 API 中，`tool_choice` 通常有三種硬性模式可選：

- **`"none"`**：強迫模型**絕對不能**使用工具（只能當成純聊天模型）。
    
- **`"auto"`**：預設模式。模型自己看著辦，想用就用，不想用就聊天。
    
- **`{"type": "function", "function": {"name": "my_specific_tool"}}`（強迫中獎模式）**：不管使用者輸入什麼（哪怕他只輸入「早安」），模型**被強迫一定要**調用 `my_specific_tool` 這個工具。這在 Data Pipeline 需要嚴格控制執行路徑時非常實用。
    

## 三、 總結：Tool Choice Model 的核心價值

把「選擇工具」跟「深度思考」這兩個職責拆開，是工業級 Agent 的標準做法：

- **省錢（Cost Effective）**：用 local 的 7B/8B 小模型去幫忙過濾與選擇工具（Tool Choice），只有在真正需要複雜大腦時才呼叫大模型，API 費用可以省下 80% 以上。
    
- **降低延遲（Latency）**：小模型吐出 JSON 的速度極快（TTFT 非常低），能讓系統的第一步響應變得非常靈敏。
    
- **防錯與降級**：如果 Tool Choice Model 發現使用者的提問根本沒有對應的工具（低於相似度門檻），系統在最前端就能直接把請求攔截下來，拒絕高昂的大模型呼叫。

## 四、 如何運作

這種架構的核心思想是：**「用最低的成本，過濾掉最簡單的任務；把最貴的算力，留給最難的挑戰。」**

它的工作流通常包含一個極輕量的「複雜度評估器」（可以是一個寫死關鍵字的 Rule-based 腳本，或是 1B~3B 的超極小模型）：

1. **使用者輸入**：_「哈囉，早安！」_
    
    - **複雜度評估**：極低（只是打招呼）。
        
    - **路由決策**：直接派本機 Mac mini 上的 **Qwen-2.5-7B** 或 **Llama-3-8B** 回覆，連網路 API 都不用呼叫。**（花費：0 元，速度：極快）**
        
2. **使用者輸入**：_「幫我寫一段 Python 幫我把這個 CSV 的空值填補，並計算移動平均線。」_
    
    - **複雜度評估**：中等（需要[[code 模式|代碼模式]]與基礎邏輯）。
        
    - **路由決策**：指派本機的 **Llama-3-8B** 配合 Docker 沙箱執行。
        
3. **使用者輸入**：_「這是我過去一年的量化回測日誌，裡面有三次大幅度回撤。請幫我結合現有的總體經濟數據（附檔 PDF），分析我的策略在什麼樣的利率環境下會失效，並提出改進計畫。」_
    
    - **複雜度評估**：極高（需要超大上下文 [[RAG|RAG]] + 深度長文本推理）。
        
    - **路由決策**：本地小模型頂不住了，路由閘門立刻將任務打包，往上傳遞給雲端最頂級的模型（如 **Claude 3.5 Sonnet** 或 **Gemini 1.5 Pro**）。
        

## 五、 為什麼要用「模型級聯（Model Cascading）」？

在商業落地或開發個人 Pipeline 時，這種設計有兩個巨大的好處：

- **把 Token 費用壓到極致**： 根據統計，一個系統裡有 60%~70% 的使用者提問其實都是簡單的閒聊、格式轉換或單一查詢。如果全部塞給進口的大模型，每個月的帳單會非常恐怖。透過這種架構，可以讓本地免費的模型處理掉大半的髒活。
    
- **兼顧隱私安全**： 複雜度評估器還可以順便兼任「資安過濾器」。如果發現使用者的指令涉及本地敏感資料，它會強制路由給 Local 模型處理，絕不讓資料上雲端。
