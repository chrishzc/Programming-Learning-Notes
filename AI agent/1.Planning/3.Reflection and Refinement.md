# 反思與精煉 (Reflection & Refinement)

> [!ABSTRACT]
> 探討如何透過輸入封裝與格式引導讓 LLM 具備反思能力，並說明如何利用最大迭代與重試限制來防範 ReAct 迴圈失控。

---

當模型進入ReAct迴圈後: 第一次的輸入經過agent程式變成第二次的輸入會帶有以下資訊

1. ==原始的系統提示詞與任務目標==

為了讓模型不忘記初衷，第二次輸入仍會包含最初的**系統指令（System Prompt）**，其中定義了工具的使用規範（如 [[1.ReAct|ReAct]] 格式：Thought/Action/Observation）以及使用者的**原始問題（User Query）**。

2. ==模型上一輪的「思考」與「指令」==

執行器會將 [[生成式 AI、LLM 概論|LLM]] 在第一輪輸出的內容（例如它寫下的 `Thought` 和輸出的 `Action` JSON）重新餵回給模型。這讓模型「記得」自己剛才打算做什麼。

3. ==工具執行的「觀察結果」（Observation）==

這是最關鍵的內容。代理人執行器（Scaffolding）在攔截並執行完工具後，會將結果封裝成一條訊息，通常==標記為 **Observation**（觀察）或 **ToolMessage**。==

- **如果執行成功**：輸入會包含工具回傳的數據（如：`Observation: 29 years`）。
- **如果執行失敗**：輸入會包含錯誤訊息（如：`Observation: Error: API timeout` 或 `Observation: File not found`）。

4. 誘導反思的「格式引導」

在 ReAct 框架中，提示詞模板會強制要求模型在看到 `Observation` 標籤後，必須先輸出下一個 **Thought（思考）**。

- 在某些高級設置中，開發者甚至會手動注入一段引導語，例如：「這是剛才執行的結果，請檢查它是否符合預期。如果不符合，請分析原因並修正計畫。」



假設使用者問：「計算 Olivia Wilde 男朋友年齡的 0.23 次方。」

**第一輪 LLM 輸出：** `Thought: 我需要先找 Olivia Wilde 的男朋友。 Action: Search(query="Olivia Wilde boyfriend")`

**執行器處理後，給 LLM 的「第二次輸入」內容會像這樣：**

**(System)**: 你是一個助手，請按 Thought/Action/Observation 格式回答... **(User)**: 查詢 Olivia Wilde 的男朋友是誰，並計算他的年齡的 0.23 次方。 **(Assistant)**: Thought: 我需要先找 Olivia Wilde 的男朋友。 Action: Search(query="Olivia Wilde boyfriend") **(Tool/Observation)**: **Observation: Olivia Wilde started dating Harry Styles after ending her engagement...**

LLM 為什麼會反思？

當 LLM 讀到這段「第二次輸入」時，它發現對話歷史中多了一個 `Observation`。根據它接受過的**對齊訓練**和**提示詞合約**，它會執行以下邏輯：

1. **對比**：將 `Observation` 中的事實（Harry Styles）與上一輪的 `Thought` 進行語意關聯。
2. **評估**：判斷目前的數據是否足以回答原始任務。
3. **生成反思**：如果發現還缺年齡，它會輸出下一個 `Thought`：「查詢結果顯示是 Harry Styles，現在我還需要找他的年齡。」


## 一、 預防「過早結束」（任務未完成，但模型覺得好了）

這種情況通常源於模型的「過度自信」或對工具回傳結果的誤判。

- **強化「自我反思與評估」（Reflection & Refinement）機制**：
    - 在循環中加入專門的==**自我批評==（Self-criticism）**步驟。
    - **引導式反思**：在工具執行完畢後，執行器（Scaffolding）可以注入特定的提示詞，例如：「這是剛才的執行結果，請對比原始目標，分析目前的數據是否真的足以回答問題？」。
- **高品質的「工具描述契約」**：
    - 模型過早結束有時是因為它覺得可以靠「內部過時知識」回答。在工具描述（Description）中明確強調哪些任務**必須**依賴工具提供的事實，能強迫模型在==斷言完成前先完成必要的調用==。
- **引入「人類在環」（Human-in-the-Loop）審批**：
    - 對於具備破壞性或高價值的任務，在模型輸出「最終答案（Final Answer）」前，設置一個**執行鉤子（Execution Hook）**攔截結果，交由人工確認任務是否真的達標。
- **檢測終止原因（stop_reason）**：
    - 監控模型的終止標誌。如果模型在沒有調用預期工具的情況下直接返回 `end_turn`，系統應發出警告或==自動觸發「完整性檢查」==的提示詞。

## 二、 預防「陷入死循環」（任務已完成，但模型覺得還沒好）

這類情況通常是因為工具報錯、格式解析失敗或模型陷入邏輯陷阱，導致 Token 浪費與成本飆升。==需要設置硬性限制==

- **設置「硬性最大迭代次數」（max_iterations）**：
    - 這是在執行器層面最基本的安全柵欄。開發者必須設置一個上限（通常建議在 **5 至 10 次**之內），一旦達到次數模型仍未停止，則由系統強制退出循環並報錯。
- **配置「最大重試限制」（max_retry_limit）**：
    - 當工具調用因異常拋出錯誤時，限制模型針對同一個錯誤嘗試修正的次數（例如 [[Key Frameworks & Protocols|CrewAI]] 預設為 2 次），防止模型反覆生成錯誤的參數或代碼。
- **強制生成文本回應（Enforce Text Response）**：
    - 可以自定義 **ToolCallConfig**。當循環次數過多時，提示詞會動態切換，要求模型：「目前已嘗試多次，請根據目前已獲得的所有資訊，給出盡可能完整的總結，並停止調用工具」。
- **重複模式檢測（Pattern Detection）**：
    - 執行器應監控對話歷史。如果發現模型連續兩次發出**完全相同的工具調用請求（相同的 JSON 參數）**且得到相同的 Observation，系統應識別為陷入僵局並強制干預。
- **資源與成本監控**：
    - 由於每次循環都會讓上下文視窗（Context Window）迅速膨脹（累積歷史推理與觀察事實），應監控 Token 消耗量。當上下文過長導致推理品質下降時，主動遞交（Handoff）給另一個乾淨內容視窗的[[AI Agent 概論|子代理人]]。

總結預防策略表

| 策略類型     | 針對問題  | 具體手段                                      |
| -------- | ----- | ----------------------------------------- |
| **內在邏輯** | 過早結束  | 增加自我反思步驟、優化工具描述語意。                        |
| **外部約束** | 陷入死循環 | 設定 `max_iterations`、限制 `max_retry_limit`。 |
| **互動介入** | 兩者皆可  | 實施 Human-in-the-loop、使用執行鉤子過濾結果。          |
| **流程管理** | 兩者皆可  | 使用 [[MCP Client & MCP Server|MCP]] [[code 模式|代碼模式]]精簡決策流、多代理人任務遞交。                |

**核心原則**：不要讓模型在「真空」中自問自答。好的代理人系統必須具備強健的**外部腳手架（Scaffolding）**，在模型思考的每一輪都進行數據校驗與邊界防禦
