# MCP 客戶端與伺服器 (MCP Client & MCP Server)

## Abstract

對比 MCP 客戶端與伺服器在職責、運作機制與部署位置上的差異。從 **"Agent Skills (智慧體技能)"** 的動態視角出發，深入解析「MCP + 代碼模式」如何透過邊緣端計算，神級節省 98.7% 的 Token 成本與 2026 年最新工業趨勢。

## 一、 核心角色與定位：用「技能（Skills）」的角度來解構

在 MCP 架構中，大模型（LLM）本身只是個空的大腦，而 MCP 則是幫它隨插即用的「技能擴充包」。

```
[使用者] ──> [MCP 客戶端 (agent)] <── JSON-RPC 2.0 ──> [MCP 伺服器 (skills)]
                    │                                             │
             (控制上下文與 LLM)                             (調度本地資源/Docker)
```

- **MCP 客戶端 (Client) ──「主廚的大腦與看守所長」**
    
    活在主機環境中（Host，如 Cursor、Claude Desktop 或 LangGraph 主程式）。它自己沒有任何技能，但它負責與雲端 LLM 溝通、管理對話視窗（Context Window），並扮演看守所長，負責攔截並審查高風險的操作。
    
- **MCP 伺服器 (Server) ──「躺在書架上的專業技能書」**
    
    它是提供具體功能（如連接 Postgres、操作 Git）的外部小程式。**它本身不包含 LLM**，只是封裝了技能的標準操作步驟。
    
- **所謂的「安裝 MCP」**
    
    就是把這本技能書的「啟動捷徑與參數」登記到大腦的履歷表（設定檔）裡。**未安裝前**，AI 會說它不會；**安裝之後**，AI 就知道隨時可以去「翻閱」這項超能力。
    

## 二、 運作機制與職責差異表

| **功能維度**               | **MCP 客戶端 (Client) ── agent                                   | **MCP 伺服器 (Server) ── 技能橋樑**                 |
| ---------------------- | ------------------------------------------------------------- | -------------------------------------------- |
| **主動/被動**              | **主動方。** 負責向伺服器調閱技能清單，並在需要時對伺服器發起工具調用指令。                      | **被動方。** 靜態躺在硬碟裡，直到大腦要用它時，才在背景被啟動並回應請求。      |
| **數據處理**               | 負責上下文與資安管理。決定要把哪些「技能說明書」餵給 LLM，攔截 L3 級別的危險操作。                 | 負責商務邏輯的執行。調用本地硬體資源（資料庫、檔案系統、Docker API）來幹髒活。 |
| **動態載入**<br>**(要用再讀)** | 為了不撐爆 Context Window，**平常只加載技能大綱**。當 LLM 判定需要某項技能時，才動態讀取詳細參數。 | 平常保持休眠或低耗能待命，收到指令時才由 Client 拉起進程（Spawn）執行。   |
| **傳輸協定**               | 實作 JSON-RPC 2.0 的傳輸管理，處理 Stdio 或 SSE（Server-Sent Events）的連接。  | 遵循 JSON-RPC 2.0 規範來回應請求並回傳結構化數據。             |

## 三、 記憶優化策略：傳統模式 vs 現代代碼模式（省下 98.7% Token 的真相）

### 1. 傳統模式的痛點：搬運數據的「上下文膨脹」

傳統的 Agent 遇到要分析 50MB 的日誌檔案時，MCP 客戶端會把這 50MB 的大數據**全部讀進對話歷史（Shared Context）中**再丟給 LLM。這會導致 Token 費用暴增、LLM 開始幻覺，甚至直接撐爆 Context Window。

### 2. 現代進階優化：MCP + 代碼模式 (Code Mode)

> 💡 **核心思維：**「用『技能/代碼（Code）』去就近親近『數據（Data）』，而不要把『數據』搬運給『大腦（LLM）』。」

- **大腦不搬數據，只寫劇本（約 500 Token）：**
    
    LLM 不要求讀取 50MB 的檔案。相反地，LLM 利用它強大的寫程式技能，自己編寫了一段原生的 Python 數據清洗腳本。
    
- **邊緣端無情執行：**
    
    MCP 客戶端將這段腳本（劇本）打包，發送給本地的 **MCP Filesystem/Docker Server**。Server 收到後，直接在你的電腦本機（邊緣端）用 CPU/記憶體對 50MB 數據進行無情清洗與計算。
    
- **精簡回傳（約 100 Token）：**
    
    腳本在本機跑完後，只將篩選出的最後 5 行「黃金數據/結論」回傳給雲端大腦。
    
- **經濟效益：**
    
    原本需要 15 萬 Token 的跨網路大型傳輸任務，瞬間縮減至 2,000 個 Token 內，**顯著節省 98.7% 的空間與金錢成本。**
    

## 四、 2026 行業新趨勢：Docker 官方 MCP Toolkit 革命

在現代工業級開發中，如果讓 MCP Server 直接在你的實體電腦上亂跑、寫入檔案是非常危險的。為了實現極致的安全與無腦部署，目前的標準實作已演進為 **Docker MCP Toolkit** 架構：

```
[MCP 客戶端] ──> [Docker Desktop (圖形介面/管理員)]
                       │
                       ├──> [Docker 容器: MCP GitHub Server]
                       └──> [Docker 容器: 獨立隔離監獄 (Sandbox)] ──> 默默打工/完工銷毀
```

1. **全面容器化（Containerization）：**
    
    連 MCP Server 本身，現在都會被打包成一隻安全的 Docker 容器在背景運行。它具有極高的連通靈活性，可以是本地（Local）輕量化腳本，也可以是遠端（Remote）雲端服務。
    
2. **一鍵擴充技能：**
    
    開發者不需要再用終端機打一堆 `npm` 或 `pip` 指令。直接在 Docker Desktop 的圖形介面中，像逛 App Store 一樣「點選並下載」各種開源 MCP 插件（如 GitHub, PostgreSQL）。
    
3. **無痛控制隔離沙盒（Sandbox）：**
    
    MCP Server 作為「拿著特許證明的通訊官」，透過安全通道控制 Docker 引擎。那些「髒數據」與待執行的 Python 腳本會被關在最底層的隔離監獄（沙盒）裡，隨時準備在完工、洗完資料後，被無情拋棄與銷毀。
    

## 五、 💡 本章總結

- **MCP 客戶端（Client）** 負責 **「對內管理大腦與上下文」**，它是規劃者。
    
- **MCP 伺服器（Server）** 負責 **「對外作為技能包去調度數據」**，它是執行者。
    

透過這套「大腦安裝技能，要用時再讀取，交給本機動態執行」的標準化 JSON-RPC 契約，大語言模型徹底從一個只能文字聊天的機器人，蛻變為能夠在邊緣端發動無情計算的工業級自動化大腦。
