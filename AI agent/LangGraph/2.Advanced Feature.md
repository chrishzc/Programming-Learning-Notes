# LangGraph 進階功能

> [!ABSTRACT]
> 本章介紹 LangGraph 的四大進階功能：Cyclic Graphs（循環圖與自動重試）、Human-in-the-loop（中斷與審批）、Multi-Agent Orchestration（多 Agent 協作調度）與 Time-Travel Debugging（時空旅行調試）。

---

## 1. Cyclic Graphs (循環圖與自動重試)

在傳統的線性鏈（Chain）中，程式只能從 A 走到 B 再走到 C，一旦中間出錯或不達標，流程便會中斷。

**Cyclic Graphs（循環圖）** 允許節點之間形成「迴圈」，讓 AI 有能力**自我修正（Self-Correction）**。

### 💡 核心概念

最經典的應用場景是 **「程式碼生成與測試（Code Generation & Execution）」** 或 **「[[RAG]] 檢索評估」**：

1. **Node A ([[生成式 AI、LLM 概論|LLM]])**：生成一段 Python 程式碼或 SQL 語法。
    
2. **Node B (Executor)**：實際執行這段程式碼，發現產生了 `SyntaxError`（報錯）。
    
3. **Conditional Edge (判斷)**：檢查執行結果。如果成功 $\rightarrow$ 走到 `END`；如果失敗 $\rightarrow$ 帶著錯誤訊息**連線回 Node A**。
    
4. **Node A ([[生成式 AI、LLM 概論|LLM]]) 重新修正**：看到錯誤訊息，重新修正程式碼，再次送入循環。
    

### 🛠️ 底層如何運作？

它是透過 **`Conditional Edges`（條件邊）** 實現的。你會寫一個路由函數（Router Function），這個函數會檢查當前的 `State`（例如 `state['errors']` 是否有值）。

- 如果有錯，路由函數回傳 `"llm_fix_node"`；
    
- 如果沒錯，回傳 `END`。
    
    LangGraph 就會根據這個回傳值，把指標指回原本的節點。
    

## 2. Human-in-the-loop (人類協同：中斷與審批)

AI 雖然強大，但在涉及高風險決策（例如：自動下單交易、修改資料庫、寄出正式郵件給客戶）時，我們必須讓人工審批。這就是 **Human-in-the-loop (HITL)**。

### 💡 核心概念

LangGraph 允許你在圖的執行過程中設置「檢查點（Checkpoint）」**和**「中斷（Interrupt）」**。 當流程走到某個敏感節點（例如：`execute_trade` 實際下單節點）之前，系統會自動**暫停執行 (Pause)**，將當前的所有狀態保存下來，等待人類的操作（核准/拒絕/修改參數）後，再**在獲得核准後恢復執行 (Resume)** 繼續往下走。

### 🛠️ 底層如何運作？

1. **持久化層（[[3.Persistence Layer|Checkpointer]]）**：在編譯圖時，你必須傳入一個記憶體或資料庫檢查點（例如 [[3.Persistence Layer#3. Savers (Postgres, Sqlite, Memory)|`MemorySaver()`]] 或 [[3.Persistence Layer#3. Savers (Postgres, Sqlite, Memory)|`SqliteSaver()`]]）。
    
2. **編譯時指定中斷點**：
```python
    # 在編譯時，指定在進入 "execute_trade" 節點前必須先中斷
    app = workflow.compile(checkpointer=memory, interrupt_before=["execute_trade"])
    ```
    
3. **執行與喚醒**：當你 `app.stream()` 執行時，它走到該節點就會觸發中斷並暫停執行。此時你可以透過 API 或 UI 秀給用戶看，用戶點擊「同意」後，你只需呼叫 `app.update_state()` 更新狀態，再重新傳入原來的 `thread_id` 繼續執行即可。
    

## 3. Multi-Agent Orchestration (多 Agent 協作調度)

當一個任務太複雜（例如：同時要爬網頁、做數據分析、寫技術報告），叫單一一個 [[生成式 AI、LLM 概論|LLM]] 做好所有事情通常效果很差。更好的做法是「分工合作」。

### 💡 核心概念

將大任務拆解成多個專業的子 Agent（每個 Agent 在 LangGraph 中其實就是一個 **Node**），並定義一個「主導者（Supervisor/Router）」來負責分派任務。

- **Agent A (Researcher)**：專門負責查資料。
    
- **Agent B (Coder)**：專門負責寫程式碼和畫圖。
    
- **Agent C (Writer)**：專門負責把資料整理成 Markdown。
    

### 🛠️ 底層如何運作？

主要有兩種常見的架構設計：

1. **中心化（Supervisor）模式**：有一個 [[4.Function Calling Mechanics#LLM as Orchestrator.md|Supervisor]] 節點，它是一個 [[生成式 AI、LLM 概論|LLM]]。其他 Agent 執行完後，一律把結果回傳給 Supervisor，由 Supervisor 決定下一個該輪到誰發言，或者是否可以結束。
    
2. **去中心化（Choreography）模式**：Agent 之間直接透過條件邊進行交接（例如：A 做完直接交給 B，B 覺得不行再退回給 A），不需要一個中央協調者。
    

- **State 的關鍵設計**：在多 Agent 協作時，通常會使用特殊的 ==`Annotated[list, add_messages]`==，讓不同 Agent 產生的對話紀錄能以「追溯附加」的方式整合進全域的 `State` 中，避免互相覆蓋。
    
#### `Annotated[list, add_messages]`
在預設情況下，LangGraph 的 `State` 更新邏輯是**直接覆蓋 (Overwrite)**。
如果 **Node A** 回傳了 `{"messages": ["哈囉"]}`，這時 `State` 的 `messages` 是 `["哈囉"]`。 接著，**Node B** 回傳了 `{"messages": ["你好嗎"]}`。

因為預設是覆蓋，這時 `State` 的 `messages` 就會**變成 `["你好嗎"]`**，原本的 `"哈囉"` 直接消失了！這在對話型 Agent（Chatbot）或多 Agent 協作中是個災難，因為我們會遺失所有的對話歷史。

### 2. 結構拆解

為了不讓資料被覆蓋，Python 的 `typing.Annotated` 派上用場了。它的語法結構是： `Annotated[資料型態, 處理這個資料的函式 (Reducer)]`
```python
from typing import Annotated
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    # 這行意思是：這個欄位型態是 list，但請用 add_messages 這個規則來更新它
    messages: Annotated[list, add_messages] 
```

### 這裡的 `add_messages` 是什麼？

它是 LangGraph 內建的一個 **Reducer 函式**。它的功能非常聰明，主要做兩件事：

1. **如果傳入的是新訊息**：它會把新訊息自動 `append`（附加）到原本的 `list` 後面。
    
2. **如果傳入的訊息帶有相同的 `id`**：它會識別出這是同一則訊息，並用新內容更新（Update）舊訊息（這在串流輸出或特定時空旅行修改訊息時非常有用）。
    

### 3. 實際運作範例

有了 `Annotated[list, add_messages]` 之後，我們來看看剛才的流程會變成怎樣：

- **初始狀態**：`messages` 為 `[]`
    
- **Node A 執行完畢**，回傳：
```python
    return {"messages": [HumanMessage(content="你好")]}
    ```
    
    - _此時 State 的內容_：`[HumanMessage(content="你好")]`
        
- **Node B (LLM) 接著執行完畢**，回傳：
```python
    return {"messages": [AIMessage(content="很高興認識你")]}
    ```
    
    - _此時 State 的內容_（因為 `add_messages` 觸發了附加機制）： `[HumanMessage(content="你好"), AIMessage(content="很高興認識你")]`

## 4. Time-Travel Debugging (時空旅行調試)

這是一個在複雜分散式系統或 Agent 系統中非常夢幻的功能。

### 💡 核心概念

因為 LangGraph 在每一次節點執行完畢後，都會透過 `Checkpointer` 將當前的整個 `State` 拍一張「快照（Snapshot）」，並賦予一個唯一的版本號（`config` 中的 `checkpoint_id`）。

**時空旅行** 意指你可以：

1. **查看歷史 (Replay)**：調出這個任務在步驟 3、步驟 5、步驟 8 的所有變數狀態。
    
2. **分支重試 (Fork/Forking)**：如果執行到第 10 步發現 AI 開始產生幻覺（或者是程式拋出異常），你可以直接**將狀態強制倒退回第 7 步**，修改第 7 步的某些輸入參數或 Prompt，然後從第 7 步重新分叉（Fork）出一條新的執行路徑。
    

### 🛠️ 底層如何運作？

1. **讀取歷史**：透過 `app.get_state_history(config)` 可以拿到完整的歷史快照列表。
    
2. **時空旅行重試**：你可以挑選歷史中某個特定的 `checkpoint_id`，直接將它作為 `config` 傳入 `app.stream(None, config=target_config)`，LangGraph 就會完全從狀態歷史記錄中，從那個時間點繼續往下跑。這在測試 Prompt 差異或排查邊緣個案（Edge case）時極度強大。
