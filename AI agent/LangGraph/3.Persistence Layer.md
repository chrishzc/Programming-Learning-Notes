# LangGraph 持久化層

> [!ABSTRACT]
> 本章深入探討 LangGraph 的持久化設計：執行緒內的短期記憶與狀態快照 (Checkpointer)、跨執行緒的長期記憶 (Store) 以及底層物理儲存介面 (Savers，包含 Postgres, Sqlite, Memory)，並說明編譯注入的依賴分離設計。

---

## 1. Checkpointers (Short-term / Thread-scoped)

### 💡 核心概念：執行緒內的「短期記憶與狀態快照」

這是 LangGraph 最常用也最核心的持久化機制。它的作用範圍被限制在 Thread（執行緒/對話串）之內。

- **運作邏輯**：當你和 AI 開始一段對話（給定一個 `thread_id="user_123_chat_A"`），Checkpointer 就會開始工作。圖中的節點每執行完一步，它就會把當前的整個 [[1.Architecture#支柱三：Shared State (共享狀態 ── 進出房間都要背著的背包)|State]] 拍一張快照存下來。
    
- **主要用途**：
    
    - **維持對話上下文**：讓 AI 記得這場對話的歷史記錄。
        
    - **實現進階功能**：我們前面聊到的 [[2.Advanced Feature#2. Human-in-the-loop (人類協同：中斷與審批)|Human-in-the-loop 中斷審批]] 和 [[2.Advanced Feature#4. Time-Travel Debugging (時空旅行調試)|Time-Travel 時空旅行]]，完全是建立在 Checkpointers 錄下的這些快照之上。
        
- **限制**：它是隔離的。`thread_A` 絕對看不到 `thread_B` 的記憶。
    
### Thread
在 LangGraph 中，一個 Thread 就是一個**擁有完整時空歷史紀錄的獨立對話 Session**。
#### 1. Thread 包含什麼？

當你在 LangGraph 中指定一個 `thread_id` 時，系統會在資料庫（如 SQLite 或 Postgres）中為你分配一個獨立的儲存空間。這個 Thread 內部主要由兩大核心要素定義：

##### 核心要素 A：`thread_id`（唯一識別碼）

- 這是一個由你自定義的字串（例如：`"user_chris_chat_001"`）。
    
- 只要 `thread_id` 相同，LangGraph 就會認定這是同一個人的同一場對話，並自動載入該 Thread 的歷史狀態。
    
- 不同的 `thread_id` 之間是**完全隔離**的（A 看不到 B 的資料）。
    

##### 核心要素 B：`checkpoint_id`（歷史快照軸）

一個 Thread 內部並不是只存一個最終狀態，而是像 Git 的 Commit 紀錄一樣，圖的**每個節點執行完畢（Superstep），都會在該 Thread 下生成一個帶有 `checkpoint_id` 的快照**。

> **也就是說：**
> 
> $\text{Thread} = \text{thread\_id} + [ \text{Checkpoint}_1, \text{Checkpoint}_2, \text{Checkpoint}_3, \dots ]$

#### 2. 程式碼中如何定義與使用 Thread？

在呼叫圖的 `.invoke()` 或 `.stream()` 時，你不需要在系統內預先建立 Thread，而是直接在 `config` 參數中傳入 `thread_id`，LangGraph 就會自動幫你建立並管理它。

##### 寫法範例（新版 API 標準語法）：
```python
# 定義你的執行配置
config = {
    "configurable": {
        "thread_id": "session_bitcoin_bot_01"  # 這行就定義了 Thread
    }
}

# 第一次互動：啟動此 Thread 
events = app.stream({"messages": [("user", "分析一下 BTC 阻力位")]}, config=config)
for event in events:
    print(event)

# 第二次互動：同一個 Thread，AI 會記得剛才聊過 BTC
events = app.stream({"messages": [("user", "那 ETH 呢？")]}, config=config)
```

#### 3. Thread 在進階功能中的角色

為什麼說 Thread 是 LangGraph 的精髓？因為前面提到的進階功能，都是在操作這個 Thread 內部的快照軸：

- **[[2.Advanced Feature#2. Human-in-the-loop (人類協同：中斷與審批)|Human-in-the-loop (中斷)]]**：當圖走到敏感節點前中斷時，Thread 的指標會停留在目前的 `checkpoint_id`，並將狀態標記為 `interrupted`。當人類核准後，系統直接從該 Thread 的最新快照接續執行。
    
- **[[2.Advanced Feature#4. Time-Travel Debugging (時空旅行調試)|Time-Travel (時空旅行)]]**：你可以呼叫 `app.get_state_history(config)` 撈出這個 Thread 所有的 `checkpoint_id`。如果你想回到過去，只要在 config 中同時指定 `thread_id` 與舊的 `checkpoint_id`，就能從那個特定的歷史時間點分叉（Fork）出新的流程。

## 2. Stores (Long-term / Cross-thread)

### 💡 核心概念：跨執行緒的「長期記憶與全域知識庫」

在 LangGraph 較新的版本中，引入了 `BaseStore` 的概念，為了解決 [[3.Persistence Layer#1. Checkpointers (Short-term / Thread-scoped)|Checkpointer]] 「無法跨執行緒共享」的痛點。

- **運作邏輯**：它是一個鍵值/文件資料庫（Key-Value / Document Store）。它獨立於圖的執行流程之外，所有的 Thread 都可以對同一個 Store 進行讀寫（`store.get()` 或 `store.put()`）。
    
- **主要用途**：
    
    - **使用者偏好記憶（User Profile）**：使用者在 `thread_A` 提到「我不喜歡太繁瑣的程式碼，請給我精簡的範例」，AI 可以把這個偏好存入 Store。當使用者隔天開啟全新的對話 `thread_B` 時，AI 依然可以從 Store 撈出這個偏好。
        
    - **全域知識累積**：多個 Agent 在不同的工作流中蒐集到的新資訊、新工具 API Key，或者是優化後的 Prompt，都可以丟進 Store 共享。
        

## 3. Savers (Postgres, Sqlite, Memory)

### 💡 核心概念：記憶要存放在什麼「實體儲存介面」

不論是 [[3.Persistence Layer#1. Checkpointers (Short-term / Thread-scoped)|Checkpointers]] 還是 [[3.Persistence Layer#2. Stores (Long-term / Cross-thread)|Stores]]，它們都只是抽象的邏輯層。真正要把資料寫進電腦裡，需要透過 **Savers（儲存驅動）**。LangGraph 官方提供了幾種開箱即用的選擇：

- **Memory (`MemorySaver`)**：
    
    - **特點**：資料全部存在記憶體（RAM）中。
        
    - **場景**：**本地開發測試（Local Debugging）**、單元測試。==程式關閉後，所有狀態即被清除。==
        
- **Sqlite (`SqliteSaver` / `AsyncSqliteSaver`)**：
    
    - **特點**：==輕量級檔案資料庫，會在本機生成一個 `.db` 檔案。==
        
    - **場景**：適合中小型專案、個人自動化腳本或本地端的持久化需求，既能保留資料又不需要繁瑣地部署資料庫服務。
        
- **Postgres (`PostgresSaver`)**：
    
    - **特點**：企業級關聯式資料庫驅動。
        
    - **場景**：**生產環境（Production）**。當你的 AI 服務要上線、需要處理高併發（Concurrency）、或是分散式架構時，首選 Postgres(PostgreSQL)。==(要用的話要先建一個PostgreSQL資料庫給agent連接)==
    
### 為什麼官方偏愛 Postgres 而非 MySQL？

- **JSONB 的強大支援**：LangGraph 的 `State` 裡面可以存各種複雜的 Python 物件、字典、模型對話紀錄。Postgres 擁有極度強大且成熟的 `JSONB` 資料型態，能進行高效的 JSON 內部欄位索引與查詢。MySQL 雖然現在也有 JSON 支援，但在複雜物件的處理效能與生態上，Postgres 在 AI 開發領域幾乎是公認的標準配備。
    
- **技術債與生態圈**：LangChain/LangGraph 團隊在開發時，優先選擇了資料庫生態最豐富、最適合儲存 Agent 狀態的 Postgres。
    

#### 如果你非用其他SQL不可怎麼辦？

你必須自己繼承 LangGraph 的 `BaseCheckpointSaver` 類別，手動去寫 SQL 語法（例如 `CREATE TABLE`、`INSERT`、`UPDATE`）來自行實作如何把狀態存進 MySQL。除非公司或專案有強烈的硬性規定，否則**極度建議直接使用 Postgres，可以省下大量自行實作的時間**。

## 實務上如何組合它們？

在寫程式碼時，我們會以模組化方式組合它們。一個標準的持久化建構程式碼長這樣：
```python
from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.graph import StateGraph

# 1. 先決定實體儲存介面：用 Sqlite 存在本地檔案中
memory_db = SqliteSaver.from_conn_string("my_agent_memory.db")

# 2. 定義你的圖工作流
workflow = StateGraph(MyState)
# ...（加入節點與邊）...

# 3. 編譯時，把這個 Saver 當作 checkpointer 餵進去
# 這時你的圖就內建了「執行緒短期記憶(Checkpointer)」與「實體儲存(Sqlite)」
app = workflow.compile(checkpointer=memory_db)
```

這樣一來，你的 AI 就有了持久化狀態（記憶），即使重啟終端機，只要傳入同一個 `thread_id`，它就能立刻接續上一次的話題！

## ==為什麼編譯時要把 Saver 當作 checkpointer 餵進去?==

這涉及到了 LangGraph 的「架構分離」設計哲學。

在寫程式時，我們通常會經歷兩個階段：

1. **設計圖的骨架**（有哪些 Node、Edge 怎麼連、條件是什麼）。
    
2. **讓圖跑起來**（實際執行並保存狀態）。
    

### 為什麼要叫 `checkpointer`？

在 LangGraph 的術語中，[[3.Persistence Layer#1. Checkpointers (Short-term / Thread-scoped)|Checkpointer]] 是一個**抽象的角色（Role）**，意思叫「檢查點管理器」。它的職責是：**當圖在運行時，負責在每個節點結束後去拍快照、管理 Thread、提供時空旅行的功能。**

...而你建立的 `saver`（不論是 `MemorySaver`、`SqliteSaver` 還是 `PostgresSaver`），則是**實體（Implementation）**，負責決定這些快照最後要寫到哪裡去。

### 依賴注入（Dependency Injection）

當你呼叫 `workflow.compile(checkpointer=saver)` 時，你編譯時將指定的 Saver 注入 Checkpointer 抽象介面。

> _「報告引擎，我已經把這張圖的邏輯（節點、連線）設計好了（`workflow`）。現在我要把它編譯成一個可運行的應用程式。請你在它運行的時候，把 `saver` 當作你的 `checkpointer`（檢查點管理器）來使用。這樣一來，每次只要有節點執行完畢，你就知道要把狀態抄寫到我指定的那個資料庫裡了！」_

### 這樣設計有什麼好處？

這樣做做到了「邏輯與儲存完全分離」：

- 你的圖邏輯（Nodes, Edges）寫完後，完全不用去改裡面的程式碼。
    
- **本地測試時**：`workflow.compile(checkpointer=MemorySaver())`（快速、免安裝）。
    
- **小型部署時**：`workflow.compile(checkpointer=SqliteSaver(...))`（存成本地檔案）。
    
- **大型上線時**：`workflow.compile(checkpointer=PostgresSaver(...))`（存入企業級資料庫）。
