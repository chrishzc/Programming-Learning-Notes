# LangGraph 生產與部署

> [!ABSTRACT]
> 本章深入探討 LangGraph 在生產環境中的典型失效模式（無限循環、工具調用幻覺、上下文溢出）、防禦性設計（步數限制、訊息修剪、Pydantic 顯式校驗）以及底層部署託管基礎設施（LangGraph Server、vLLM 加速推理）。

---

## 主幹一：Typical Failure Modes (典型的失敗/崩潰模式)

這是 [[AI Agent 概論|Agent]] 上線後的「典型的失效模式」，每一個都是資源消耗的痛點：

### 1. Infinite loops (無限循環)

- **現象**：當你設計了包含自我修正的「循環圖（Cyclic graph）」時，如果 [[生成式 AI、LLM 概論|LLM]] 生成的程式碼或結果一直出錯，它就會不斷回到 Node A 修正、再進 Node B 測試、再出錯、再回到 Node A...。
    
- **災難**：在沒有防護引導下，AI 會在一分鐘內陷入無限循環幾十次，直到把你幾百塊美金的 API 額度瞬間消耗完，或者讓系統卡死在死循環裡。
    

### 2. Tool call hallucinations (工具調用幻覺)

- **現象**：[[生成式 AI、LLM 概論|LLM]] 決定要呼叫某個工具，但它開始「產生幻覺」，自己捏造了根本不存在的工具名稱（例如你只有 `place_market_order`，它自己發明了 `execute_super_trade`），或者雖然叫對了工具，但裡面的參數完全亂填、甚至漏掉必要欄位。
    
- **災難**：這會導致你的後端 Python 程式碼直接拋出 `KeyError` 或 `TypeError`，導致整張圖在執行中途崩潰死亡。
    

### 3. Context length overflow (上下文長度溢出)

- **現象**：因為我們用了 `Annotated[list, add_messages]`，對話紀錄會像滾雪球一樣愈來愈長。當一個 Thread 互動了幾十輪後，整個訊息歷史的 Token 量會變得極度巨大。
    
- **災難**：當長度超過了大模型（如 GPT 或本地 Llama）的「最大上下文視窗（Context Window）」限制時，API 會直接拒絕服務並傳回 400 Bad Request，讓這場對話徹底死掉。
    

## 主幹二：Defensive Design (防禦性設計)

針對上面的典型的失效模式，LangGraph 提供了三面「防禦機制」，這是寫生產環境程式碼時必加的防護：

### 1. Recursion limits (遞歸極限/硬性步數限制)

- **拆解**：這是用來克制 **Infinite loops（無限循環）** 的大絕招。
    
- **作法**：[[1.Architecture|LangGraph]] 在執行時允許你設定一個 `recursion_limit` 參數（例如設定為 20 步）。如果這個 Agent 陷入無限循環，在圖的節點之間跳轉超過 20 次，[[1.Architecture|LangGraph]] 引擎會**在第 21 步啟動時「強制中斷並拋出 Exception」**。這成功幫你中斷執行以防止死循環，保住你的錢包。
    

### 2. Message trimming/pruning (訊息修剪與剪枝)

- **拆解**：這是用來對抗 **Context length overflow（上下文溢出）** 的限制機制。
    
- **作法**：你可以在圖運行期間，或者在餵給 [[生成式 AI、LLM 概論|LLM]] 節點之前，加上一個「修剪函數」（如 `trim_messages`）。這個函數會強行限制上下文長度，例如：「只保留最近的 10 則對話紀錄」或者是「當 Token 超過 4000 時，自動把最早的 5 則對話切掉，但強制保留最前面的 System Prompt」。這樣上下文就能永遠保持在安全長度。
    

### 3. Explicit schema validation (顯式架構驗證)

- **拆解**：這是用來防禦 **Tool call hallucinations（工具幻覺）** 的防線。
    
- **作法**：這就是我們前面聊到的 [[4.Tools|Pydantic]]。在工具或節點前，用強型態的 [[4.Tools|Pydantic]] 進行 `ValidationError` 的捕捉。如果 [[生成式 AI、LLM 概論|LLM]] 傳進來的 JSON 欄位少了一個或型態不對，程式碼會在呼叫實體 API 之前，攔截這個錯誤，並把 [[4.Tools|Pydantic]] 報錯的訊息當作下一輪的 Input  自動餵回給 [[生成式 AI、LLM 概論|LLM]]（「你剛剛傳入的參數少寫了 side，請重新填寫」），讓它能夠根據精準的程式錯誤進行自我修正。
    

## 主幹三：Infrastructure (基礎設施與託管)

防護網做好了，接下來是決定把這一整套 LangGraph 程式部署到什麼樣的底層硬體與伺服器架構上：

### 1. Agent Server (Auto-persistence / 自動持久化伺服器)

- **拆解**：在實際商業線上環境，你不能只跑一個 `.py` 腳本，你需要處理多個用戶同時連線（高併發）的問題，而且要幫每個用戶自動開闢 `thread_id` 並妥善存檔。
    
- **實作方案**：官方有推出 **LangGraph Server**。它是一個開箱即用的 Web 伺服器架構，你只需要部署已編譯的 Graph，它會自動對外暴露標準的 RESTful API 和 WebSocket 串流接口，並且**內建高效率的持久化層**（幫你自動連好 Postgres 或 Redis，自動管理 Checkpoints、Threads 和中斷處理）。你不需要自己手動編寫 FastAPI 從頭去刻伺服器。
    

### 2. GPU hosting (vLLM / H100 instances / 開源算力部署)

- **拆解**：當你的 Agent 規模變大、或者是你的交易策略/客戶資料涉及商業機密，不想傳給 OpenAI 等第三方雲端公司時，你通常會選擇在公司內部或雲端（如 AWS、Lambda Labs、RunPod）租用內建 **H100** 等高效能顯示卡的伺服器，來跑**開源的大模型（如 Llama 3、Mistral）**。
    
- **核心技術 (vLLM)**：在自己託管 GPU 跑模型時，後端通常會使用 **vLLM**（目前業界公認最強大的 LLM 推理加速引擎）。它利用了 PagedAttention 技術，能讓單張顯示卡在處理高併發的 Agent 請求時，記憶體佔用極小、推理速度（Tokens per second）提升數倍，完美承載 [[1.Architecture|LangGraph]] 頻繁呼叫 [[生成式 AI、LLM 概論|LLM]] 的巨大算力需求。
