# LangGraph 工具調用與擴展

> [!ABSTRACT]
> 本章拆解 LangGraph 中工具（Tools）的創建與執行上下文：包含 @tool 裝飾器、Pydantic 參數校驗、ToolRuntime 共享狀態讀寫、以及 Stream writers 串流進度更新機制。

---

## 第一部分：Creation（創建工具）

要讓 [[生成式 AI、LLM 概論|LLM]] 理解並正確使用你的工具，你必須告訴它三件事：**這個工具有什麼用**、**需要傳入什麼參數**、以及**參數的型態是什麼**。這三個概念是相輔相成的：

### 1. `@tool` decorator（工具裝飾器）

- **說明**：這是最快、最優雅的工具創建方式。你只需要寫一個普通的 Python 函數，並在上面加上 `@tool` 裝飾器，LangGraph 就會自動把它包裝成 [[生成式 AI、LLM 概論|LLM]] 看得懂的工具物件。
    
- **範例**：
```python
    from langchain_core.tools import tool
    
    @tool
    def get_crypto_price(ticker: str) -> float:
        """取得指定加密貨幣的當前市場價格。"""
        # 實際的 API 請求邏輯...
        return 65000.0
    ```
    

### 2. Docstring descriptions（文件字串描述）

- **說明**：你有看到上面程式碼中用三個引號包起來的 `"""取得指定加密貨幣的當前市場價格。"""` 嗎？這就是 **Docstring**。
    
- **為什麼極度重要？**：這段文字**不是**給寫程式的人看的，而是**直接當作 Prompt 餵給 [[生成式 AI、LLM 概論|LLM]] 看的**！[[生成式 AI、LLM 概論|LLM]] 就是靠這段描述來判斷：「哦！使用者現在想知道價格，我應該去呼叫 `get_crypto_price` 這個工具。」如果你的 Docstring 寫得很模糊，[[生成式 AI、LLM 概論|LLM]] 就會錯誤地調用工具。
    

### 3. Pydantic / JSON schemas（參數型態定義）

- **說明**：工具需要輸入參數（例如上面的 `ticker: str`）。LangGraph 底層會利用 Python 的型態提示（Type Hints）或 **Pydantic** 模型，自動把這個工具轉化成標準的 **JSON Schema**。
    
- **目的**：這會強制 [[生成式 AI、LLM 概論|LLM]] 只能回傳符合格式的參數（例如：`{"ticker": "BTC"}`），如果 [[生成式 AI、LLM 概論|LLM]] 試圖傳入錯誤的型態（例如傳了一個數字），在底層就會被攔截，確保你的 Python 程式不會拋出異常。

#### 如果需要複雜參數的JSON schemas（使用 Pydantic）

如果你的工具參數非常多、或者有非常嚴格的邏輯限制（例如：數量不能小於 0、輸入的幣別必須是特定字串），這時我們會結合 **Pydantic** 來定義：
```python
from pydantic import BaseModel, Field
from langchain_core.tools import tool

# 1. 定義參數的 Pydantic 模型
class OrderArgs(BaseModel):
    symbol: str = Field(description="交易對名稱，例如 'BTCUSDT' 或 'ETHUSDT'")
    side: str = Field(description="下單方向，只能是 'BUY' 或 'SELL'")
    amount: float = Field(gt=0, description="下單數量，必須大於 0")

# 2. 把這個模型餵給 tool 裝飾器
@tool(args_schema=OrderArgs)
def place_market_order(symbol: str, side: str, amount: float):
    """執行加密貨幣的市價單下單交易。"""
    # 你的下單 API 邏輯...
    return f"成功以 {side} 建立 {amount} 個 {symbol} 的市價單"
```

## 第二部分：Execution Context（執行期上下文）

傳統的 LangChain 工具是非常「孤立」的，它被呼叫、執行、然後回傳結果，它**不知道**現在整個系統的狀態是什麼。 而 LangGraph 帶來了突破性的進階功能 —— **讓工具擁有整張圖的視角（Execution Context）**。

### 1. ToolRuntime (State & Store access)

- **說明**：在新版的 LangGraph 中，工具在執行時可以主動去存取全域的 **[[1.Architecture#支柱三：Shared State (共享狀態 ── 進出房間都要背著的背包)|State（當前對話狀態）]]** 或者是 **[[3.Persistence Layer#2. Stores (Long-term / Cross-thread)|Store（長期記憶庫）]]**。
    
- **應用場景**：假設你寫了一個 `execute_order`（執行下單）的工具。這個工具被觸發時，不需要 [[生成式 AI、LLM 概論|LLM]] 傳入使用者的 API Key，工具可以直接透過 `ToolRuntime` 去 Store 裡面撈出目前使用者的加密金鑰來用。這樣既安全，又減少了 [[生成式 AI、LLM 概論|LLM]] 傳錯參數的風險。
- LangGraph 為了保護大腦，不讓==工具直接存取 `State` 物件==，所以專門設計了一個名為 `ToolRuntime` 的「代理介面 (Proxy)」，讓工具只能透過它，安全地讀取 [[1.Architecture#支柱三：Shared State (共享狀態 ── 進出房間都要背著的背包)|State]] 和 [[3.Persistence Layer#2. Stores (Long-term / Cross-thread)|Store]]。==但要在程式碼中指定要讀state的哪個數值==

### 2. State injection & updates（狀態注入與更新）

- **說明**：傳統工具只能回傳「字串（String）」給 [[生成式 AI、LLM 概論|LLM]] 聽。但 LangGraph 允許工具在執行完畢後，**直接去修改或更新全域的 [[1.Architecture#支柱三：Shared State (共享狀態 ── 進出房間都要背著的背包)|State]]**。
    
- **應用場景**：工具執行完畢後，不只把結果回傳給 [[生成式 AI、LLM 概論|LLM]]，還能順便在 [[1.Architecture#支柱三：Shared State (共享狀態 ── 進出房間都要背著的背包)|State]] 裡打個勾，記錄 `{"is_database_updated": True}`，讓接下來的節點可以直接根據這個狀態走不同的路由。
    

### 3. Stream writers (Progress updates / 串流進度更新)

- **說明**：當工具需要執行很久（例如：需要跑歷史回測 30 秒、或者去網頁爬取大量資料）時，如果會造成使用者介面停頓與等待，使用者體驗會極差。
    
- **功能**：`Stream writers` 允許工具在執行到一半時，**一邊做一邊往外「推播」目前的進度訊息**（例如：「[1/3] 正在下載歷史數據...」、「[2/3] 正在計算技術指標...」）。這讓前端可以同步顯示一個精美的載入進度條，而不需要等到整個工具全部跑完才吐資料。

### 4. Context 與 Execution Context 差異

- **Node 間的上下文（State）**： 這是整張圖的「共用資料夾」。它是隨著時間推進、節點依序執行而改變的動態記憶（例如：對話歷史紀錄、當前任務進度、AI 的思考鏈）。各個節點會輪流讀取並更新它。
    
- **Tools 的執行期上下文（Execution Context）**： 這是工具執行時的「特權系統與周邊環境」。它打破了傳統工具「黑盒子」的限制，不隨時間累積記憶==是完全沒有生命週期的臨時環境(執行完就會消失)==，而是**在工具運行當下，連通模型記憶（讀寫 State/Store）並能透過專屬管道向前端即時推送進度。**
